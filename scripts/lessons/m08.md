## 1. The Mental Model

Kubernetes is a system of control loops. You declare an intended state in the API, and independent controllers observe actual state and try to narrow the difference. Updating a Deployment describes a release. It does not mean a release finished, received traffic, or succeeded from a user's perspective.

Think of a theater production with a run sheet, roster, and venue. The run sheet decides how many staffed booths are required. A staffing coordinator replaces absent operators, and a venue coordinator decides where each booth fits. The audience should see only booths that have reported readiness. Someone can be present and employed without being ready for customers. The system becomes dependable when each role has a clear definition of success and the status it reports is meaningful.

| Object | Owns or represents | Useful evidence |
| --- | --- | --- |
| Pod | One scheduled unit of one or more closely coupled containers | Conditions, restarts, last termination, logs |
| ReplicaSet | A desired number of matching Pods | Desired, current, ready counts |
| Deployment | Controlled changes to a Pod template across revisions | Revision, available replicas, rollout conditions |
| Service | Stable discovery and transport to ready backends | Selectors, port mapping, EndpointSlices |
| Ingress | HTTP routing rules interpreted by an installed controller | Assigned address, controller status, host/path route |
| HorizontalPodAutoscaler | Target replica changes driven by measured signals | Current and desired replicas, valid metrics |

Pods are replaceable and their IPs can change. Treat local container files as ephemeral unless they live on appropriate storage. Replicas need the same configuration and service behavior but need not run on the same node. Maintain compatibility when old and new revisions overlap. A tightly coupled sidecar can share Pod networking and explicit volumes with the app. Independently scalable work generally belongs in a separate workload.

## 2. Core Architecture & How It Works Under the Hood

```text
 kubectl / GitOps -> API server <-> etcd
                         ^
                         | observe and write desired / actual state
             +-----------+---------------+
             |                           |
 Deployment controller -> ReplicaSets   scheduler selects a node
             |                           |
             +--> Pod objects <---- kubelet on chosen node
                                         |
                                 runtime + CNI + volumes
                                         |
 client -> Service / Ingress -> ready endpoint -> container
```

### API, desired state, and ownership

The API server authenticates and authorizes operations, runs admission, validates objects, and persists them in etcd. Controllers watch API objects. The Deployment controller manages ReplicaSets that reflect revisions of its Pod template. Each ReplicaSet creates or removes Pods to satisfy its desired count. Owner references help controllers and garbage collection track what should follow an owner's lifetime. Labels are used for grouping and selection. A label that changes accidentally can disconnect traffic or create overlapping selectors. Keep the Deployment selector stable and ensure it matches its Pod template.

`spec` is desired state and `status` is observed state. A generation change alone does not say that the controller acted on it. Compare observed generation or conditions, and then test the user-facing behavior. Reconciliation is asynchronous. Commands such as `kubectl apply` can succeed before dependent Pods exist.

### Scheduling and node execution

The scheduler filters nodes against available requested resources and placement rules, scores eligible nodes, then binds an unscheduled Pod to a node. The kubelet on that node asks the container runtime to obtain the image and start the containers. The network plugin prepares Pod networking and the volume system supplies declared storage. A Pending Pod can be unscheduled or scheduled but still waiting for a mount, image, or another dependency. Kubernetes events and the Pod's conditions tell you which step failed.

CPU requests influence placement and relative CPU shares. CPU limits can throttle execution. Memory requests influence placement, while exceeding a memory limit can cause a kill. A Pod can be evicted under node pressure regardless of its application's events or logs. Requests that are too low encourage dense placement and distort utilization percentages used by resource autoscalers. Requests that are too high can leave otherwise capable nodes unable to accept more work. Tune requests from measured steady-state and startup use, validate under load, and leave room for rolling updates and evictions.

### Networking and probes

A Pod receives an IP and containers in that Pod share a network namespace. A ClusterIP Service provides a stable address and a DNS name. Clients use the Service port, which maps to its backend target port. Service selectors and readiness contribute to Endpoints and EndpointSlices used by the cluster dataplane. The dataplane implementation can differ across clusters. Verify endpoint addresses and matching workload labels before investigating low-level networking. `NodePort` exposes a selected node port, typically across nodes. `LoadBalancer` asks a platform integration to configure an external or internal balancer. A controller for Ingress interprets host and path rules, selects Services, and can terminate TLS. Creating only an Ingress object cannot provision a controller or guarantee a DNS record or certificate.

Health checks drive different actions. A startup probe protects a slow initialization period and gates subsequent probes. A liveness failure can cause the container to restart. A readiness failure removes it from ready endpoints while leaving the process running. Liveness should detect a stuck process, such as an application that can never respond. A remote database outage should rarely restart every client. Readiness should indicate whether this instance can productively participate. During termination, allow time for routing changes, draining, and application shutdown. A load balancer may not see endpoint state changes instantaneously, so the app needs to handle graceful closure as well.

### Release safety and capacity

A rolling update runs old and new Pods concurrently until readiness and availability criteria are met. A surge temporarily increases Pod count. An unavailable budget controls the permitted reduction in available instances. Higher surge can shorten deployment if the cluster has room. A PodDisruptionBudget regulates voluntary disruptions such as eviction for node maintenance, subject to the workload's constraints. Plan Deployment strategy and disruption policy together.

For CPU-driven HPA, the controller periodically compares measured utilization with a target such as 70% of CPU requests. An approximate relationship is desired replicas equals current replicas times current metric divided by target metric, rounded up, then adjusted for missing metrics, configured bounds, tolerances, and scaling behavior. If four replicas observe 105% and the target is 70%, that base calculation proposes six. The HPA needs a metrics source and valid CPU requests. It creates more desired replicas, while node autoscaling is a separate control loop that may have to add infrastructure. Stabilization reduces flapping. Use queue age, backlog, or concurrency where that signal better predicts waiting time than CPU.

## 3. Complete Command, Query & Python Syntax Reference

### Inspect declared and observed state

```bash
kubectl config current-context
kubectl -n gallery-lab get pods -l app=queue-display -o wide
kubectl -n gallery-lab describe deployment queue-display
kubectl -n gallery-lab get events --sort-by=.metadata.creationTimestamp
kubectl -n gallery-lab get endpointslices -l kubernetes.io/service-name=queue-display
```

`current-context` states the configured cluster and context alias. Verify it before mutation, especially when using a shared kubeconfig. `-n` scopes namespaced resources. `-l` is a label selector and `-o wide` adds transport and placement columns to the Pod list. `describe` combines details and events, including rollout counts and conditions. `get events` sorts visible recent events by creation timestamp. Events are time-limited evidence, so save relevant diagnostic information during an incident. The EndpointSlice query finds backend records for the Service. Once the lab starts, expect two available Pod endpoints and a Deployment with two ready replicas.

For a repeatedly crashing Pod, `kubectl -n gallery-lab logs POD -c display --previous` requests logs for the prior terminated instance of the named app container. Substitute the observed Pod name. Omit `--previous` to inspect current output. Use the exit state and events alongside logs because a container can fail before logging is possible. `kubectl ... port-forward service/queue-display 8081:80` is a local diagnostic tunnel for a selected backend, not a simulation of all production network paths. The number before the colon is the client-side listening port and the second is the Service port.

### Model runtime configuration

A ConfigMap holds non-sensitive settings. A Secret is meant for sensitive values and uses base64 encoding in its standard representation, which by itself supplies no confidentiality. Production design requires narrow service-account authorization, appropriate storage encryption, controlled secret source and rotation, and careful application logging. Keep real secrets outside public manifests. A projected file can update after a delay, while an environment variable is captured when the process starts. Make reload semantics explicit. For immutable release configuration, update a versioned name or Pod template checksum and let the Deployment replace Pods.

For CPU and memory, key units are `100m` for 0.1 CPU and `128Mi` for 128 mebibytes of memory. Set container requests under `resources.requests` and ceilings under `resources.limits`. Very tight liveness timeouts can cause a feedback loop when CPU is throttled. Observe recovery under pressure with the same runtime quotas rather than blindly tuning probe frequency.

For an HPA, `autoscaling/v2` supports the `HorizontalPodAutoscaler` kind and explicit metric targets plus policy. Configure a `scaleTargetRef` with API version `apps/v1`, kind `Deployment`, and its exact name. `minReplicas` and `maxReplicas` bound the action. For a resource metric of type `Resource` and name `cpu`, choose a target type `Utilization` and an `averageUtilization` percentage. If the workload is managed by HPA, avoid repeatedly applying a conflicting fixed replica count. Verify observed metrics and scaling behavior before using the autoscaler to manage capacity. An HPA is optional for the local rollout lab because a bare kind cluster may lack metrics-server.

## 4. End-to-End Real-World Reference Example

An art gallery is releasing a queue-display API. Display terminals need a route that stays useful while a new revision starts. Deploy two replicas, probe each revision, then demonstrate why an unhealthy replacement does not become a backend. Use a disposable kind cluster named `gallery-lab`, Docker, `kubectl`, and two terminals. A minimal Python server suffices for this control-loop exercise. An actual public API should use a production ASGI server and production network controls.

```text
gallery-lab/
  display.py
  Dockerfile
  workload.yaml
```

**`display.py`**

```python
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
import json
import os
import signal
from threading import Thread
from time import monotonic

STARTED = monotonic()
SITE = os.environ.get("SITE_NAME", "Gallery")
FAIL_READY = os.environ.get("FAIL_READY", "0") == "1"

class Display(BaseHTTPRequestHandler):
    def do_GET(self):
        ready = not FAIL_READY and monotonic() - STARTED >= 3
        status, response = {
            "/live": (200, {"alive": True}),
            "/ready": (200 if ready else 503, {"ready": ready}),
            "/queue": (200 if ready else 503, {"site": SITE, "ready": ready}),
        }.get(self.path, (404, {"error": "not found"}))
        body = json.dumps(response).encode()
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

with ThreadingHTTPServer(("0.0.0.0", 8080), Display) as server:
    # BaseServer.shutdown must run on a different thread from serve_forever.
    signal.signal(signal.SIGTERM, lambda *_: Thread(target=server.shutdown).start())
    server.serve_forever()
```

Set `FAIL_READY` only for the deliberate local test. `monotonic()` measures elapsed time without wall-clock corrections. The server binds an address available to kubelet probes through the Pod network. `ThreadingHTTPServer` handles requests on separate threads. The SIGTERM handler requests a server-loop shutdown from another thread, which shows why containers can stop gracefully. A production server also needs timeouts, draining and resource-aware concurrency.

**`Dockerfile`**

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY --chmod=0444 display.py .
USER 10001:10001
CMD ["python", "-u", "display.py"]
```

The exec-form array starts the Python process directly, unbuffered, with a non-root numeric identity. The copied app file is explicitly readable regardless of the permissions in the build context. The app needs no runtime package install or write access to the application directory.

**`workload.yaml`**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: display-settings
data:
  SITE_NAME: River Gallery
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: queue-display
spec:
  replicas: 2
  progressDeadlineSeconds: 45
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: queue-display
  template:
    metadata:
      labels:
        app: queue-display
    spec:
      automountServiceAccountToken: false
      containers:
        - name: display
          image: gallery-display:v1
          imagePullPolicy: IfNotPresent
          envFrom:
            - configMapRef:
                name: display-settings
          ports:
            - name: http
              containerPort: 8080
          resources:
            requests: {cpu: 50m, memory: 32Mi}
            limits: {cpu: 250m, memory: 96Mi}
          securityContext:
            runAsNonRoot: true
            readOnlyRootFilesystem: true
            allowPrivilegeEscalation: false
            capabilities:
              drop: ["ALL"]
          readinessProbe:
            httpGet: {path: /ready, port: http}
            periodSeconds: 2
            timeoutSeconds: 1
          livenessProbe:
            httpGet: {path: /live, port: http}
            periodSeconds: 10
            timeoutSeconds: 1
---
apiVersion: v1
kind: Service
metadata:
  name: queue-display
spec:
  selector:
    app: queue-display
  ports:
    - port: 80
      targetPort: http
```

The ConfigMap's data becomes process environment for the app. The Deployment permits one extra Pod and requires continued availability of both existing replicas before replacing them. The 45-second progress deadline records a condition; Kubernetes does not automatically roll back just because that deadline expires. Matching selector and template labels give ownership and routing consistency. The container port is named `http` so both probes and Service can refer to it. Each probe sends an HTTP GET with the configured cadence and timeout. The request and limit values are lab budgets to measure and revise. Disable the default service-account token mount because the app needs no Kubernetes API access. `IfNotPresent` uses the image loaded into the local cluster. For shared deployments, publish immutable artifacts and reference stable digests. No Service type is supplied, so it defaults to ClusterIP.

```bash
kind create cluster --name gallery-lab
docker build -t gallery-display:v1 .
kind load docker-image gallery-display:v1 --name gallery-lab
kubectl --context kind-gallery-lab create namespace gallery-lab
kubectl --context kind-gallery-lab -n gallery-lab apply -f workload.yaml
kubectl --context kind-gallery-lab -n gallery-lab rollout status deployment/queue-display --timeout=60s
kubectl --context kind-gallery-lab -n gallery-lab port-forward service/queue-display 8081:80
```

The build tag names the local artifact, and `kind load` copies it into the specified cluster's nodes. `--context` explicitly selects the disposable cluster, and `create namespace` creates the lab location. `apply -f` submits the file's objects. `rollout status` watches the Deployment and stops waiting after the bounded timeout. The final command runs in the foreground. In a second shell call `curl -fsS http://127.0.0.1:8081/queue`; expect `{"site": "River Gallery", "ready": true}`. Keep the initial server running.

Run `kubectl --context kind-gallery-lab -n gallery-lab set env deployment/queue-display FAIL_READY=1` to set an environment entry in the Pod template and create a new revision. Inspect Pods and EndpointSlices after the new Pod appears. It should run and fail readiness. Service-ready endpoints should still be from the old revision. A `rollout status` watch with a short `--timeout=30s` should fail to observe rollout completion. The forwarded origin should still serve a ready Pod. For Service routing evidence independent of the forwarded session, evaluate the EndpointSlice readiness conditions. Roll back with `kubectl --context kind-gallery-lab -n gallery-lab rollout undo deployment/queue-display`. Undo selects the previous revision when no revision number is supplied. Watch the rollout again and check `/queue`. Stop the tunnel with Ctrl+C. After the exercise, remove the disposable local cluster with `kind delete cluster --name gallery-lab`.

## 5. Common Pitfalls & Debugging Playbook

### Running Pods, missing traffic

**Symptom:** Direct requests to a Pod respond, while the Service returns timeouts or connection failures.
**Root Cause:** The selector, namespace, readiness condition, or target port does not correspond to the intended backend.
**Diagnostic:** Compare `kubectl -n gallery-lab get pods --show-labels` and `kubectl -n gallery-lab get service queue-display -o yaml`, then inspect EndpointSlices in the same namespace. Check endpoint readiness and the reported backend port.
**Fix:** Align selectors and template labels, fix the specific readiness failure, and confirm the named target port matches the listener. Keep same-namespace discovery explicit.

### Pending with no visible process

**Symptom:** A Pod never reaches Running and produces no app logs.
**Root Cause:** Scheduling, mounting, or image retrieval failed before the app could start.
**Diagnostic:** Use `kubectl -n gallery-lab describe pod POD` with the observed Pod name. Inspect `PodScheduled`, node assignment, and event reason. A scheduling failure differs from `ImagePullBackOff`.
**Fix:** Adjust justified requests or placement and provide capacity for scheduling errors. For image errors, verify the actual image digest, platform, registry availability, and legitimate pull credentials.

### Repeated crash with non-obvious cause

**Symptom:** A Pod shows `CrashLoopBackOff`, or it restarts under load.
**Root Cause:** Backoff is a restart delay. The cause may be an exception, a bad configuration, a health failure, or memory exhaustion.
**Diagnostic:** Inspect `lastState.terminated`, the container events, and prior logs using `--previous`. Compare latency of the probe to CPU throttling and check for `OOMKilled`.
**Fix:** Address the specific termination cause first. Use a startup probe for slow startup, preserve safe resource headroom, and keep dependency failures from triggering broad liveness restarts.

### HPA metrics unknown or replicas oscillate

**Symptom:** The HPA lists unknown utilization or repeatedly alternates between replica counts.
**Root Cause:** Metric collection or CPU requests are missing, or scale-down reacts faster than the workload stabilizes.
**Diagnostic:** Inspect `kubectl describe hpa NAME`, using the actual autoscaler name and namespace. Check metric availability through `kubectl top pods` and compare requests with measured behavior.
**Fix:** Establish the metrics pipeline and valid requests. Choose a relevant metric, set safe replica bounds, and add stabilization and rate policies demonstrated under representative load.

### Rollout stalls or regresses after a healthy probe

**Symptom:** The Deployment never reaches desired availability, or real traffic fails after rollout.
**Root Cause:** A surge Pod cannot schedule, readiness validates only superficial behavior, or adjacent versions disagree on contract or data format.
**Diagnostic:** Compare available old and new replica counts, events, and behavior through the Service. Read the Deployment's progress condition and compare the released contracts.
**Fix:** Provide enough capacity for the selected strategy, use a readiness check that reflects the instance's serving ability, and test old/new interoperability. Roll back using a verified previous artifact if the new revision is unsafe.

### Project 1: Campus Dining API Rollout

**Domain:** Education

The campus dining team displays current meals across several terminals. Model the menu's non-sensitive settings separately from the service image. Define the minimum availability required during release and how an instance signals that a valid menu is loaded. Simulate a new revision that starts successfully but never becomes ready.

#### Recommended Folder Structure

Use campus-dining with app/menu.py, Dockerfile, deploy/deployment.yaml, deploy/service.yaml, deploy/settings.yaml, tests/test_rollout.py, and docs/rollback.md.

#### Build Milestones

1. Define Deployment, Service, readiness, and rollout criteria.
2. Demonstrate a bad revision does not receive traffic during rollout.

#### Acceptance Checklist

Observe the old replica set continuing to serve valid menu responses while the new Pod stays unready. Use endpoint conditions to verify only the right Pods are eligible, and show a successful rollback with an unchanged client-facing Service name.

### Project 2: Catalog Thumbnail Autoscaler

**Domain:** E-commerce

An online catalog generates thumbnails in bursts after bulk product uploads. Measure work duration and backlog and distinguish worker saturation from a lack of node capacity. Choose a replica signal that follows user waiting time, then account for warm-up, concurrent fetches, and downstream object storage limits.

#### Recommended Folder Structure

Use catalog-thumbnails with worker/resize.py, fixtures/test-images.txt, deploy/workload.yaml, deploy/autoscaler.yaml, tests/test_load.py, and docs/scaling-study.md.

#### Build Milestones

1. Measure resource requests and design scaling policies with sensible stabilization.
2. Run a repeatable load scenario and record scale-up and scale-down behavior.

#### Acceptance Checklist

A repeatable burst demonstrates how replicas and queue delay change. An idle interval shows the intended scale-down behavior. A downstream slowdown should not multiply load without bound, and a missing metrics feed should be diagnosable.

### Project 3: Regional Weather Gateway

**Domain:** Public safety

A regional emergency coordination team consumes a public weather test feed through a local gateway. Keep configuration and credentials separate. Operators need to distinguish a bad rollout, a mistyped upstream setting, a missing secret, and a routing problem without reading sensitive values.

#### Recommended Folder Structure

Use regional-weather with app/gateway.py, deploy/deployment.yaml, deploy/service.yaml, deploy/ingress.yaml, deploy/settings.yaml, fixtures/weather-sample.txt, tests/test_gateway.py, and docs/operations.md.

1. Separate configurations from sensitive values and document resource, probe, and routing policies.
2. Reproduce a startup failure and diagnose it using events, logs, and endpoint state.

#### Acceptance Checklist

Prove a missing or invalid setting produces a controlled readiness failure and useful sanitized diagnostics. Verify endpoint selection and the intended host and path through the selected controller. Restore the expected configuration and confirm service recovery through the real client interface.

## 7. Mastery Checkpoint Questions

### Q1. A pod should stay alive during warm-up but receive no requests. Which outcome should express that?

- A. Fail liveness continually
- B. Report not ready until warm-up completes
- C. Remove resource requests

<details>
<summary>Answer & Explanation</summary>

**Answer: B.** Readiness controls endpoint inclusion. A startup probe can delay liveness checks if initialization is slow.

</details>

### Q2. A Service has no endpoints although pods are running and ready. What should you verify first?

- A. The namespace and Service selector against pod labels
- B. Whether the Containerfile was committed
- C. The Grafana color palette

<details>
<summary>Answer & Explanation</summary>

**Answer: A.** A Service selector must match pods in its namespace. Inspect EndpointSlices to confirm the result.

</details>

### Q3. A Pod never starts and declares a request that exceeds free allocatable memory on every permitted node. Where should you begin?

- A. Pod scheduling events and node capacity
- B. The Pod's application request logs
- C. Reordering Service ports

<details>
<summary>Answer & Explanation</summary>

**Answer: A.** The scheduler cannot bind the Pod before startup. A Pod description can show scheduling reasons even when the container never produced logs.

</details>

### Q4. What happens when a Deployment reaches its progress deadline while the new revision remains unready?

- A. Every old Pod is stopped immediately
- B. The Deployment reports stalled progress, and an operator or automation can choose the recovery
- C. The API server removes all Services in the namespace

<details>
<summary>Answer & Explanation</summary>

**Answer: B.** The deadline sets an observed Deployment condition. Reconciliation and any external release policy determine subsequent behavior. Kubernetes does not automatically roll back based only on that condition.

</details>

### Q5. How does a 70% CPU-based HPA interpret current average utilization of 105% across four eligible replicas?

- A. It always keeps four replicas
- B. It always creates 105 replicas
- C. Its basic ratio proposes six replicas, before bounds and policy adjustments

<details>
<summary>Answer & Explanation</summary>

**Answer: C.** The simple formula rounds up four times 105 over 70. Missing metrics, readiness and stabilization influence the actual result.

</details>

### Q6. Outline how to distinguish a broken Service selector from an application whose container is healthy but unready.

<details>
<summary>Answer & Explanation</summary>

Inspect labels, Service selector, namespace, and EndpointSlices. Verify readiness probe results from the Pod description. With a selector mismatch the intended Pods are not selected. Matched unready Pods can be present with non-ready conditions. Confirm backend port and make an application request after fixing the actual cause.

</details>

### Q7. Describe a rollout and disruption policy for a two-replica API that must tolerate one rescheduled Pod.

<details>
<summary>Answer & Explanation</summary>

Budget capacity for enough ready replicas and one temporary surge where needed. Configure readiness and a rollout availability floor, test a deliberately bad revision, and use a disruption budget governing voluntary node disruption. Confirm scheduling headroom, placement across relevant failure domains, and end-to-end behavior during replacement.

</details>
