## 1. The Mental Model

A Linux service is a process running under a particular identity, with a working directory, an environment, and open file descriptors. Diagnosing a deployment means finding which boundary failed: path traversal, process startup, socket binding, or connectivity from the client. Changing permissions or restarting a process before identifying that boundary can erase the evidence.

Think of a service as a workshop. The filesystem provides rooms, permissions define who can enter, the process is the worker, and the listening socket is the front desk. A client can only reach the application if the front desk is open at the address it called.

| Boundary | Question to ask |
| --- | --- |
| Filesystem | Can the service user traverse every parent directory and read the resource? |
| Process | Which executable, user, environment, and working directory are in effect? |
| Socket | Which process is listening on which interface and port? |
| Network | Does the name resolve, and can packets reach that socket? |

## 2. Core Architecture & How It Works Under the Hood

```text
 shell / systemd
       |
       | execve(program, arguments, environment)
       v
 +--------------------+        open()       +----------------------+
 | process (UID, PID) | -----------------> | /srv, /etc, /var/log |
 | current directory  |     mode + ACL      | directories / files  |
 +----------+---------+                     +----------------------+
            | bind() / listen()
            v
 +--------------------+     TCP connection     +------------------+
 | 127.0.0.1:8471     | <--------------------  | curl / HTTP client |
 | kernel socket     |                         +------------------+
 +--------------------+
```

1. A shell or service manager launches a program. The child receives the configured environment and working directory and runs with an effective user and group. A relative path starts at that working directory.
2. The kernel checks execute (search) permission on every parent directory, then checks access to the file. An ACL mask can restrict the effective permissions of a named ACL entry.
3. The process binds a kernel socket. A loopback bind accepts local traffic only. A wider bind still depends on routing and firewall rules.
4. A client resolves a hostname, connects, then sends HTTP. DNS, TCP, and HTTP failures require different diagnostics.
5. On shutdown, send a termination request and allow the program to finish in-flight work. A forced kill gives the process no chance to flush or clean up.

## 3. Complete Command, Query & Python Syntax Reference (Progressive)

### Files and service identity

```bash
pwd
id
namei -l /srv/health/config.json
chmod 640 config.json
chown appuser:appgroup config.json
setfacl -m u:auditor:r-- config.json
getfacl config.json
```

- `pwd` prints the current directory. `id` prints the user, primary group, and supplementary groups. Use them in the same context as the failing service.
- `namei -l` walks a path and lists ownership and permissions along the way. A readable file is inaccessible if a parent directory denies traversal.
- `chmod 640` grants owner read/write, group read, and no access to others. The digits are sums of read (4), write (2), and execute (1).
- `chown user:group` sets the owning user and group. It requires appropriate privilege, and changing owners can affect a running deployment.
- `setfacl -m` modifies an ACL. `u:auditor:r--` grants that named user read permission subject to the ACL mask. `getfacl` shows the effective rights. Use existing principals and directory policies.

### Processes and connectivity

```bash
ps -eo pid,user,stat,args
htop
ss -ltnp
curl --fail --silent --show-error --max-time 3 http://127.0.0.1:8471/health
dig +short example.com A
kill -TERM <pid>
```

- `ps -e` selects all processes. `-o` chooses columns (ID, owner, state, command). `htop` adds a live view of resource usage when installed.
- `ss -ltnp` lists listening (`-l`) TCP (`-t`) sockets, numeric addresses (`-n`), and available process info (`-p`). Inspect the local address as well as the port.
- `curl` fails on HTTP error responses with `--fail`, hides the meter with `--silent`, retains errors with `--show-error`, and caps total time with `--max-time`.
- `dig +short name A` queries for IPv4 records with compact output. Check AAAA separately for IPv6. DNS success alone does not establish that a TCP connection is allowed by a firewall.
- `kill -TERM` requests graceful shutdown of a PID you own or administer. The argument is a specific, verified process ID, not a process name.

### Service management and SSH

```bash
systemctl --user status health-lab.service
journalctl --user -u health-lab.service -n 20 --no-pager
sshd -t
```

`systemctl --user` talks to the current user's manager. `journalctl -u` selects the unit, `-n 20` limits entries, and `--no-pager` prints directly. Use `sshd -t` with appropriate read permissions to validate SSH server config and host keys before a reload. Verify a second key-authenticated login before changing authentication policy and keep the existing administrator session open. Limit allowed SSH principals and protect private keys with strict permissions and a passphrase.

## 4. End-to-End Real-World Reference Example (Python-Centric)

A community weather station needs a local readiness endpoint that exercises access to a configuration file. Keep the bind on loopback and run under your existing account for the lab.

```text
health-lab/
  app.py
  station.txt
  probe.sh
  health-lab.service
```

**`app.py`**

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
from pathlib import Path

STATION_FILE = Path(__file__).with_name("station.txt")


class Handler(BaseHTTPRequestHandler):
    def do_GET(self) -> None:
        if self.path != "/health":
            self.send_error(404)
            return
        try:
            station = STATION_FILE.read_text(encoding="utf-8").strip()
        except OSError:
            self.send_error(503, "Station configuration unavailable")
            return
        if not station:
            self.send_error(503, "Station name is empty")
            return
        body = f"ready: {station}\n".encode()
        self.send_response(200)
        self.send_header("Content-Type", "text/plain; charset=utf-8")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)


if __name__ == "__main__":
    with HTTPServer(("127.0.0.1", 8471), Handler) as server:
        server.serve_forever()
```

Put `Harbor East` in **`station.txt`**. Run the probe with Bash. Quoting preserves a URL argument as a single word, and the default is used when the argument is missing or empty.

**`probe.sh`**

```bash
#!/usr/bin/env bash
set -eu
url="${1:-http://127.0.0.1:8471/health}"
curl --fail --silent --show-error --max-time 3 "$url"
```

From the lab directory, run `python3 app.py`. From a second terminal in that directory, run `bash probe.sh`. Expect `ready: Harbor East`. Rename `station.txt` temporarily to see the probe fail with HTTP 503, then restore it. Stop the foreground process with Ctrl+C.

**`health-lab.service`** (optional on machines with a systemd user session)

```ini
[Unit]
Description=Weather station readiness lab

[Service]
WorkingDirectory=%h/health-lab
ExecStart=/usr/bin/python3 %h/health-lab/app.py
Restart=on-failure
RestartSec=2s
NoNewPrivileges=true

[Install]
WantedBy=default.target
```

`%h` expands to the user's home directory. `WorkingDirectory` fixes relative path resolution and `ExecStart` specifies the exact program and argument. `Restart=on-failure` retries crashes with a two-second delay. `NoNewPrivileges` prevents privilege gains via execution. With the files under `~/health-lab`, copy the unit to `~/.config/systemd/user/`, run `systemctl --user daemon-reload` and `systemctl --user start health-lab.service`, then run the probe again. Inspect the journal and stop the lab with `systemctl --user stop health-lab.service`. This small HTTP server is a lab fixture. Use a supported production server for real traffic.

## 5. Common Pitfalls & Debugging Playbook

### 1. Readable config returns permission denied

**Symptom:** The file is readable according to its mode, yet the service receives EACCES.

**Root Cause:** A parent directory lacks search permission, or a named ACL entry is restricted by its mask.

**Diagnostic:** Run `namei -l /srv/app/config.json` and `getfacl /srv/app`. Compare the result with the service identity.

**Fix:** Grant only the required traversal and read access to the service group or named user.

### 2. Health check works on the host only

**Symptom:** A local probe works, but another approved client cannot connect.

**Root Cause:** The process may be bound exclusively to loopback, or the intended network path is filtered.

**Diagnostic:** Inspect the bind address with `ss -ltnp` and compare a local probe to the client result.

**Fix:** Bind to the required interface and configure the approved firewall path and access controls for that service.

### 3. Works in a shell, fails under systemd

**Symptom:** A unit fails with missing files or a different interpreter.

**Root Cause:** Service environment and working directory differ from an interactive shell.

**Diagnostic:** Inspect `systemctl --user cat health-lab.service` and `journalctl --user -u health-lab.service -n 20`.

**Fix:** Set an explicit working directory and executable, reload unit definitions, then restart and probe the service.

### 4. A restart loses recent log entries

**Symptom:** The last writes disappear whenever a process is stopped.

**Root Cause:** A forced kill bypasses cleanup or application writes were buffered.

**Diagnostic:** Compare the unit stop timeout with shutdown duration and inspect exit signals in the journal.

**Fix:** Implement graceful termination and flush important data. Reserve forced termination for processes that cannot stop within the agreed time.

## 6. 3 Standalone Practice Projects (Blueprints Only — NO CODE)

### Project 1: Secure File Handoff Auditor

**Domain:** Logistics

A dispatch team needs to verify that only the intended partner service can read overnight manifests.

#### Recommended Folder Structure
- Create a fixtures directory with sample manifests, an auditor directory with an empty audit.py file, and a tests directory with an empty test_access.py file.

#### Build Milestones
1. Define the expected identities and access policy for a manifest, its parent directories, and the inbound drop area.
2. Have the auditor report ownership, effective access, and the first inaccessible parent in a clear finding per file.
3. Exercise the audit using files owned by fixtures and record the impact of a masked ACL.

#### Acceptance Checklist
- Confirm authorized manifests pass and an unauthorized reader is rejected.
- Verify an inaccessible parent is identified even when the manifest itself has read permission.

### Project 2: Digital Exhibit Health Monitor

**Domain:** Museums and cultural heritage

A gallery team needs a reliable local availability monitor for kiosk content between opening and closing.

#### Recommended Folder Structure
- Create a monitor directory with empty probe.py and reporting.py files, and a services directory with an empty unit template.

#### Build Milestones
1. Map the kiosk service from DNS through TCP to HTTP and decide what status and response indicate healthy operation.
2. Record timestamped probes with separate failure categories and a strict maximum check duration.
3. Run the monitor under a service identity and configure bounded restart behavior and readable logs.

#### Acceptance Checklist
- Simulate an unreachable port and a valid connection returning an error, and confirm the monitor distinguishes them.
- Restart the monitor and verify its run history is still available.

### Project 3: Controlled Observatory Instrument Gateway

**Domain:** Scientific research

An instrument gateway needs a dedicated service identity, a documented bind policy, and an operator recovery procedure.

#### Recommended Folder Structure
- Create application, operations, and tests directories with empty gateway.py, recovery.md, and test_startup.py files.

#### Build Milestones
1. Document the allowed interfaces, service account, configuration ownership, and operator access policy.
2. Define readiness behavior and graceful shutdown so the gateway can stop cleanly during maintenance.
3. Add a runtime checklist that separates permissions, unit configuration, name resolution, and socket failures.

#### Acceptance Checklist
- Verify allowed operators can diagnose startup, while unrelated users cannot read configuration.
- Demonstrate bounded shutdown and recovery after a configuration error.

## 7. Mastery Checkpoint Questions

### Q1. A service reads a file with mode 640 in a directory with mode 700 owned by another user. The service is in the file's group. Why does the read fail?
- A. Group permissions require the file owner to be logged in.
- B. The service cannot traverse the parent directory.
- C. Read-only group access only works on symbolic links.
- D. The service must bind a network socket first.

<details>
<summary>Answer & Explanation</summary>

**Answer: B.** The kernel checks directory search permission while resolving the path. The file's group read permission is checked only after the kernel can reach it.

</details>

### Q2. A local probe works on port 8471 and the remote client gets an immediate connection refusal. What check most directly tests whether the process is listening only on loopback?
- A. Read the client's DNS cache.
- B. Check file ownership of the probe.
- C. Inspect the local address reported by the listening socket.
- D. Compare the system clocks on both hosts.

<details>
<summary>Answer & Explanation</summary>

**Answer: C.** A socket listed as 127.0.0.1:8471 accepts IPv4 loopback traffic only. Check the bind first before changing network policy.

</details>

### Q3. A unit consistently fails with a missing relative config path, yet launching its executable from the project directory works. Which setting addresses the difference?
- A. WorkingDirectory
- B. RestartSec
- C. WantedBy
- D. Type

<details>
<summary>Answer & Explanation</summary>

**Answer: A.** Relative paths resolve from the current working directory. Set the directory explicitly, or use absolute paths for service resources.

</details>

### Q4. A service needs to flush buffered work before exit. Which signal is the appropriate first request for a graceful stop?
- A. SIGKILL
- B. SIGSTOP
- C. SIGCHLD
- D. SIGTERM

<details>
<summary>Answer & Explanation</summary>

**Answer: D.** SIGTERM can be handled by the process so it can stop accepting work and flush. SIGKILL cannot be caught.

</details>

### Q5. A hostname resolves correctly, and curl connects but reports HTTP 503. What did the probe establish?
- A. The server's application is fully ready.
- B. Name resolution and the connection succeeded, but the HTTP peer reported unavailability.
- C. The local port must be unbound.
- D. A firewall rejected the connection before HTTP.

<details>
<summary>Answer & Explanation</summary>

**Answer: B.** Receiving an HTTP response proves an HTTP peer was reachable. Inspect service readiness, dependency state, and logs next.

</details>

### Q6. An operator must diagnose a service that starts locally but fails to read its configuration after moving to a systemd unit. Outline checks that distinguish identity, path traversal, and service environment.

<details>
<summary>Answer & Explanation</summary>

Start with the unit status and journal to identify the failing path. Confirm the effective user and group and the unit's working directory. Walk the path with `namei -l` and inspect ACLs on the first inaccessible component. Fix only the missing traversal/read permission or use an explicit configuration path, then rerun the probe.

</details>
