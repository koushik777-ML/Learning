## 1. The Mental Model

An agent harness is the application that owns the rules of a model-driven workflow. The model interprets evidence and proposes what to do next. The harness decides which operations are available, checks whether a proposal is admissible, records progress, and takes responsibility for stopping. Without that separation, a change in phrasing or model behavior can silently change permissions, spend, and side effects.

Imagine a laboratory with a scientist, a safety officer, and a contained workbench. The scientist suggests an experiment. The officer checks its authorization and records the decision. The workbench enforces the physical limit even when a decision or instrument is wrong. A capable scientist improves the proposals. The ability to enforce the limits still belongs to the other two layers.

### Assign ownership before choosing a model

| Concern | Owner | Failure if the owner is unclear |
| --- | --- | --- |
| Categorizing a request | Rules or a model with typed output | Requests drift between unrelated workflows |
| Selecting an allowed next transition | State machine | Steps run out of order or repeat indefinitely |
| Deciding whether a caller may act | Policy compiled from trusted identity and state | Text submitted as evidence becomes apparent authority |
| Measuring a total resource budget | Harness and execution environment | Parallel requests each spend the same remaining budget |
| Authorizing one consequential action | A qualified human via a stored decision | A previous approval gets reused for a changed request |
| Isolating computation | Container, VM, or dedicated worker service | A failure affects unrelated jobs or the host |

The distinction between a deterministic workflow and an agent loop is about control. In a deterministic workflow, the same state and event choose the same transition. A model can supply an event, such as “these records appear ambiguous,” without owning the transition. In a free-form loop, the model chooses both direction and stopping conditions. A useful hybrid puts a bounded loop inside a deterministic transition. Search up to a fixed limit, for example, and return enough evidence or an explicit reason it could not be found.

## 2. Core Architecture & How It Works Under the Hood

~~~text
 authenticated request
         |
         v
  ingress + tenant limits -----> immutable identity / intent
         |
         v
  persisted workflow state <-----------------------+
     |        |                                     |
     |        +--> context assembly --> model       |
     |                                  | proposal |
     v                                  v          |
  policy: validate, scope, reserve budget, dedupe   |
       | allow      | review         | deny         |
       v            v                v              |
  scoped worker   approval queue   typed stop       |
  (sandbox)          |                              |
       |          verified decision ----------------+
       v
  validate output --> checkpoint --> return or continue
~~~

### What belongs in a checkpoint

Write the durable state before you depend on it. A checkpoint commonly holds a run ID, trusted tenant ID, current state, monotonically increasing revision, operation IDs, policy version, remaining budget or budget ledger, and typed references to evidence. The database stores the compact authoritative fields. Large input and output artifacts can live in scoped storage with content hashes and retention rules.

A retry after a process crash has two possibilities. An action may never have started, or it may have finished just before the checkpoint failed. Give a side effect a stable operation ID before the first attempt. Record intent, then persist the outcome using that same ID. If the downstream operation supports idempotency, resend with the same key. When it does not, reconcile against recorded receipts before attempting another effect. Require review if the outcome is still ambiguous.

A versioned transition protects against two workers reading the same checkpoint. Worker A's update succeeds only when the revision it read is current. Worker B must reread if its conditional update affects zero rows. This compare-and-set pattern handles races in the state store. To protect a remote action already in flight, use downstream idempotency or a fencing token at the action boundary as well.

### Context windows and compaction

The model context is a working set with a hard size limit. Tokens from trusted instructions, enabled tools and their schemas, recent turns, retrieved evidence, and output reservation all occupy that window. Estimate before sending, keep operational headroom, and reconcile estimates against the provider's measured usage. A response cap limits generated output. It cannot limit earlier input growth or repeated calls.

Use different storage for different lifetimes.

- In every request, rebuild trusted policy and tool definitions from the application version. Preserve user identity and authorization outside the transcript.
- Keep recent decisions and their reasons in a machine-readable checkpoint. Model-generated summaries can propose a compact description, with citations back to durable evidence.
- Retrieve only the evidence needed for the current step. Keep provenance, timestamps, and an explicit unknown state. The summary may omit a rejected hypothesis. It must never convert a rejection into permission.
- During compaction, count the summary call itself against the run budget. If the budget will not cover it, use a deterministic trim of optional evidence or finish with a partial result.

A **context limit** caps one call. A **run budget** caps total usage across calls, delays, retries, and tool execution. A production governor should track tokens, total time, attempts per step, effect count, output size, and applicable cost ceilings. Concurrent work needs atomic reservations. Reserve input estimate plus maximum requested output before dispatch, then debit the measured amount and return unused reservations. If the provider omits usage or times out, charge conservatively until reconciled.

### Routing among models

Start with a small model or deterministic classifier for narrow, well-measured requests. Escalate when evidence conflicts, a deterministic check fails, or a calibrated uncertainty threshold is met. Model confidence expressed as free-form text is a weak routing signal. Compare it with observed accuracy by task class. The stronger route needs its own latency and token limits and the same authorization checks.

Measure cost **per successful task** at each route, including fallback calls. A low-cost model with a 50% retry rate and frequent escalation can cost more than a single capable call. Distinguish automatic escalation for uncertainty from a human approval for permission. Escalating can improve an answer. The next model still inherits the same capabilities.

### Isolation and the sandbox lifecycle

Run model-supplied computational work only through a dedicated execution boundary. Attach an explicit capability to the kind of work allowed. Prefer a purpose-built runner with named operations and typed arguments when the problem is narrow. When free-form code is genuinely necessary, decide whether the required isolation is a container or a VM-based service before exposing the capability.

| Boundary | Mechanism | Practical consequence |
| --- | --- | --- |
| Process and file visibility | Linux namespaces and scoped mounts | A job sees only a designed view of files and processes |
| Resource consumption | cgroups, timeouts, file and output quotas | Excess work fails within a bounded budget |
| Kernel exposure | Capability removal, configured seccomp and mandatory access controls | Fewer interfaces are available to the process |
| Network and identity | Explicit denial or isolated policy-controlled egress, scoped identity | Job inputs cannot grant arbitrary network destinations or account privileges |
| Stronger tenant separation | A microVM adds a guest kernel and virtual devices | Additional boundary with startup and maintenance costs |

Containers share a host kernel. A microVM introduces a hypervisor boundary and a guest kernel, and still needs patched hosts, hardened configuration, input and output validation, and a controlled worker identity. Neither isolation choice should include host-mounted credentials, management sockets, or unrestricted host filesystem mounts. Long-lived worker services may be reused. The untrusted execution context should be short-lived and discarded after each run.

A sandbox broker authenticates callers, checks a job record and image policy, supplies minimal inputs, and provisions the environment. The runner enforces limits and supervises process lifetime. After exit or timeout, collect bounded logs and validated artifacts, terminate descendants, and discard scratch storage. Treat the returned data as external input. An artifact can contain unexpected links, structure, or embedded directives even after successful computation.

### Human approval and direct or indirect prompt injection

Direct prompt injection arrives in a user-supplied request. Indirect prompt injection is material embedded in a document, web result, retrieved passage, or another system's output. Labels and delimiters help the model interpret it as evidence, but an enforcement boundary is still needed. Filter unneeded inputs, use constrained proposals, and verify the caller's scope and all data references at each tool boundary. The harness should retain enough provenance to diagnose the event and minimize disclosure in logs.

A human-in-the-loop pause stores the proposed action and releases the worker. Give the review record an expiry, a run revision, reviewer scope, and a digest of the normalized action and arguments. Require a matching valid decision on resume and atomically consume it. A changed target or argument creates a new proposal. Show enough context to the reviewer to understand risk and evidence, clearly separated from untrusted prose that might otherwise be mistaken for instructions from the review system.

## 3. Complete Command, Query & Python Syntax Reference

### Represent transitions explicitly

A finite transition table makes allowed control flow reviewable. A missing pair should fail closed through a typed, expected error. Store events with their run and revision so they can be replayed in tests independently of the model.

~~~python
from enum import StrEnum

class State(StrEnum):
    PROPOSED = "proposed"
    REVIEW = "review"
    READY = "ready"
    DONE = "done"

TRANSITIONS = {
    (State.PROPOSED, "request_review"): State.REVIEW,
    (State.REVIEW, "approval_verified"): State.READY,
    (State.READY, "effect_recorded"): State.DONE,
}

def transition(state: State, event: str) -> State:
    next_state = TRANSITIONS.get((state, event))
    if next_state is None:
        raise ValueError(f"Invalid transition: {state} + {event}")
    return next_state

print(transition(State.REVIEW, "approval_verified"))
~~~

The enum values are stable identifiers suitable for a stored state column. Each map key pairs the current state with a single verified event. The lookup returns the next state and emits `ready` in this example. Issues such as stale authorizations and in-flight effects belong at the inputs to the state machine. The event name is a declaration by the trusted harness after verification.

### Compute a per-call budget

~~~python
def plan_output_limit(
    input_estimate: int,
    context_limit: int,
    remaining_run_tokens: int,
    desired_output: int,
    headroom: int = 256,
) -> int:
    context_room = context_limit - input_estimate - headroom
    run_room = remaining_run_tokens - input_estimate
    return max(0, min(desired_output, context_room, run_room))

print(plan_output_limit(1800, 4096, 2100, 512))  # 300
~~~

Input arguments are nonnegative token counts. `input_estimate` includes tool schemas and retrieved evidence. `headroom` absorbs serialization and tokenizer mismatches. The returned integer caps the response, and zero means that the context must shrink or the request must stop. In production, reserve the total through a shared transactional ledger before dispatch. A local calculation alone is safe only when there is one budget owner.

### Separate proposal validation and execution

Use schema validation to restrict fields and types. Bind actor, tenant, credentials, and applicable policy from the request context rather than taking them as model-controlled arguments. Validate that a resource belongs to the tenant and can be used for the requested operation. Require application-specific checks such as maximum quantity, current resource revision, and expected side-effect class. Return concise structured errors and avoid feeding internal implementation details back into retries.

For a Docker-based worker, the resource concepts map to settings such as `--memory` to cap memory, `--cpus` to bound CPU scheduling bandwidth, `--pids-limit` to bound process count, `--network none` to remove ordinary network access, and `--read-only` to protect the image filesystem. A writable scratch area requires a separate size limit. A CPU bandwidth limit still allows a job to run forever at that bandwidth, so supervise wall-clock execution separately. Process startup should use an unprivileged identity and a fixed runner. Scope all engine administration to the broker and keep the management socket away from jobs.

## 4. End-to-End Real-World Reference Example

### A review gate for museum catalog amendments

A museum imports proposed corrections to public artifact descriptions. A model can summarize an amendment, but only an editor can approve the exact text that will be written. The lab runs a deterministic simulation with a mock proposal, a precise action digest, an expiry, a time-independent test clock, and an idempotent publication operation. It runs locally with no model key, network, databases, or real publication.

~~~text
museum-review/
  review_lab.py     typed proposal, approval checks, in-memory write simulator
~~~

Create `review_lab.py` with this content.

~~~python
import hashlib
import json
from dataclasses import asdict, dataclass, replace

@dataclass(frozen=True)
class Proposal:
    run_id: str
    revision: int
    artifact: str
    description: str

@dataclass(frozen=True)
class Approval:
    digest: str
    reviewer_role: str
    expires_at: int

def digest(proposal: Proposal) -> str:
    # Canonical encoding keeps field order stable across retries.
    body = json.dumps(asdict(proposal), sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(body.encode("utf-8")).hexdigest()

def publish(
    proposal: Proposal,
    approval: Approval,
    now: int,
    receipts: dict[str, str],
) -> str:
    if proposal.artifact not in {"gallery-101", "gallery-102"}:
        return "invalid resource"
    if not 1 <= len(proposal.description.strip()) <= 180:
        return "invalid description"

    operation = digest(proposal)
    if approval.reviewer_role != "editor" or approval.digest != operation:
        return "approval required"
    if now >= approval.expires_at:
        return "approval expired"

    if operation in receipts:
        return f"already published ({receipts[operation]})"
    receipt = f"receipt-{len(receipts) + 1}"
    receipts[operation] = receipt
    return f"published ({receipt})"

proposal = Proposal("review-19", 1, "gallery-101", "Handwoven linen, circa 1880.")
approval = Approval(digest(proposal), "editor", 120)
receipts: dict[str, str] = {}
print(publish(proposal, approval, 100, receipts))
print(publish(proposal, approval, 101, receipts))
edited = replace(proposal, revision=2, description="Handwoven linen, circa 1890.")
print(publish(edited, approval, 102, receipts))
print(publish(proposal, approval, 121, receipts))
assert len(receipts) == 1
~~~

Run `python review_lab.py` from the folder containing the file. The command passes the script path as the program argument to the Python interpreter, which runs the top-level demonstration once.

~~~text
published (receipt-1)
already published (receipt-1)
approval required
approval expired
~~~

The digest binds the approval to the run, revision, target, and exact text. A digest is a content identifier. In production, retrieve approval records through an authenticated path, verify that the authenticated reviewer has authority over that target, and validate the current checkpoint revision. Persist the transition and an outbox entry in the same transaction. Give the publisher the stable operation ID and store its receipt even after the reviewer exits. A completed run then answers status reads from its receipt, while pending or expired approvals cannot create new effects. A test double verifies business behavior before there is any isolated worker or remote publisher.

## 5. Common Pitfalls & Debugging Playbook

### 1. The run stops immediately after compaction

**Symptom:** A request still approaches its context limit even after older turns are summarized.

**Root Cause:** The estimator counts messages but omits tool schemas, output reservation, or large retrieved records.

**Diagnostic:** Add a per-call breakdown of token estimates by component and compare the total with provider-reported input usage under the same model version.

**Fix:** Assemble context from typed, budgeted sections. Reserve output space first and cap the number and size of evidence chunks. Keep trusted policy outside summarization.

### 2. Spending jumps for runs with parallel steps

**Symptom:** Each call stays below its per-call limit, yet runs exceed the expected total.

**Root Cause:** Two dispatchers read the same balance and allocate it independently.

**Diagnostic:** Compare reservation IDs, amounts, and timestamps in the run ledger. Reconstruct the reserved plus spent total before each dispatch.

**Fix:** Reserve capacity atomically, reconcile measured usage to each reservation, and make repeated reconciliation idempotent.

### 3. A changed proposal appears already approved

**Symptom:** Reviewers approve a description, then an edited description is sent on the same workflow.

**Root Cause:** Approval was keyed to the run or a vague action name without revision and argument binding.

**Diagnostic:** Compare the normalized proposal the reviewer saw with the proposed operation at the executor. Match revision, digest, reviewer scope, and expiration.

**Fix:** Require an unexpired approval for the exact versioned action and verify it at the execution boundary. Ask for a new decision on any edit.

### 4. Finished jobs leave scratch space or child processes behind

**Symptom:** Worker storage fills overnight and tasks accumulate in termination states.

**Root Cause:** Cleanup is tied to successful completion or tracks only the initial process.

**Diagnostic:** Compare sandbox creation and destruction records and count orphaned jobs after forced timeouts. Examine storage use by job ID.

**Fix:** Supervise the whole execution scope, enforce a destruction deadline, publish bounded cleanup outcomes, and reconcile orphaned environments periodically.

### 5. Escalation improves accuracy and breaks latency targets

**Symptom:** Hard examples score better, but most standard tasks now take two model calls.

**Root Cause:** The router treats mild uncertainty as universal escalation, without measuring accuracy or latency by task class.

**Diagnostic:** Compare first-pass acceptance, escalation reason, p95 total time, and cost per successful run for each class against a single-call baseline.

**Fix:** Calibrate thresholds using representative labeled examples. Use cheap deterministic validation where possible, and reserve a bounded escalation path for evidence conflicts.

## 6. Three Standalone Practice Projects

### Project 1: Isolated Spreadsheet Formula Lab

**Domain:** Accounting education

A course uses synthetic invoice examples to teach spreadsheet arithmetic. Learners submit an exercise name and a list of numbers. A bounded runner evaluates named arithmetic exercises and returns a score with a short explanation. It handles zero divisors, malformed rows, and out-of-bounds inputs predictably, including when an exercise description contains arbitrary text.

#### Recommended Folder Structure

Create formula_lab with types.py, limits.py, runner.py, and result.py. Create tests with test_admission.py, test_resources.py, and test_cleanup.py. Put synthetic fixtures in fixtures.

#### Build Milestones

1. Design strict input shapes, filesystem isolation, and execution budgets.
2. Verify the worker cannot reach host files or the network, and stops on time.

#### Acceptance Checklist

Record admission, execution, and cleanup outcomes under one run identifier. Store only bounded outputs and tie failures to specific checks. An oversized request fails before worker allocation. A valid small exercise completes with measured runtime and a checked result. A timeout terminates the execution scope and leaves its scratch area gone. A deliberately absent input gives a typed validation error and calls no arithmetic operation.

### Project 2: Editorial Screening Queue

**Domain:** Publishing

A journal needs a screening workflow for article titles and short abstracts. The system may prepare recommendations and quote attributed evidence. An authorized editor decides whether to publish or return the result for revision. Simultaneous editing and approval must produce an unambiguous outcome.

#### Recommended Folder Structure

Create screening with ingest.py, proposal.py, policy.py, approvals.py, and publish.py. Create tests with test_approval_lifecycle.py and test_permissions.py. Save the rules and review lifecycle in docs.

#### Build Milestones

1. Define input handling and an explicit approval transition before any publish action.
2. Verify untrusted document text cannot change workflow permissions.

#### Acceptance Checklist

Bind approval to the article revision and full outbound content. Reconcile the publisher's receipt after retry and make the final state observable. A reviewer with the wrong scope cannot approve. An older approval cannot release a new revision. A client retry does not cause a second publication. Revocation or expiry while the item waits yields an explicit closed decision and a reason.

### Project 3: Research Summary Budget Manager

**Domain:** Research administration

A university office generates short summaries of reports with large appendices. The task has a strict spend and runtime budget. It should report partial results honestly when evidence is incomplete and preserve source attribution after compaction.

#### Recommended Folder Structure

Create report_summary with state.py, budgets.py, context.py, routing.py, and evidence.py. Create test_budget_races.py, test_compaction.py, and test_resume.py in tests.

#### Build Milestones

1. Define state checkpoints, compaction rules, and bounded model routing.
2. Verify interrupted jobs resume and terminate at the configured work limit.

#### Acceptance Checklist

Track reservations and reconcile measured costs without double-charging a repeated telemetry event. Compare routing accuracy, latency, and cost per successful task on a small labeled dataset. Parallel substeps cannot exceed the run's available budget. Evidence source IDs remain attached after compaction. Resuming does not repeat confirmed work. Missing evidence yields a partial result with a clear reason and record of any unused budget.

## 7. Mastery Checkpoint Questions

### Q1. Retrieved text instructs an agent to use a privileged tool. How should the harness interpret it?

- A. As a trusted system instruction
- B. As untrusted data subject to policy enforcement
- C. As approval granted by the document author

<details><summary>Answer & Explanation</summary>

**Answer: B.** Keep instruction authority separate from retrieved content. Enforce permissions outside model output.

</details>

### Q2. A sandbox runs with no network access but unlimited CPU and memory. Which essential isolation controls are missing?

- A. Additional tool descriptions
- B. A longer context window
- C. Resource limits and deadlines

<details><summary>Answer & Explanation</summary>

**Answer: C.** Control compute, memory, lifecycle, and output as well as filesystem and networking.

</details>

### Q3. Two parallel calls each read a 500-token remainder and each reserve 400 tokens locally. Which change enforces the run cap?

- A. Shorten the name of the model
- B. Use one shared ledger with atomic conditional reservations
- C. Reduce the waiting time after the first request

<details><summary>Answer & Explanation</summary>

**Answer: B.** One successful reservation leaves only 100 tokens available. The second request must fit that remainder or stop. Return unused capacity after measuring actual usage.

</details>

### Q4. An approved package description changes while the job is paused. What should happen on resume?

- A. Accept the existing approval because the job ID is the same
- B. Ask the model whether the change matters
- C. Validate the new digest, reject the old approval, and obtain a decision on the new revision

<details><summary>Answer & Explanation</summary>

**Answer: C.** An approval binds authority to an exact payload and version. Authorization must be independently verified at execution time.

</details>

### Q5. The model sees the correct policy text, yet proposes an action outside the caller's permissions. Where should the proposal be rejected?

- A. At the server's policy or tool-admission boundary
- B. In the browser after the operation
- C. After the result is summarized

<details><summary>Answer & Explanation</summary>

**Answer: A.** Authorize before effects occur, using the authenticated caller and current resource state. A structured proposal is still untrusted.

</details>

### Q6. Design the retained state when summarizing a long transcript before a pending approval. What stays outside the textual summary?

<details><summary>Answer & Explanation</summary>

Keep the run identity, actor and tenant, pending operation digest and revision, policy version, approval status and expiry, budget ledger, and source evidence references as structured records. Preserve a short recent context useful to the model and a cited summary of relevant discarded turns. Compaction never grants approval or changes the recorded scope.

</details>

### Q7. A worker lost its connection as it tried to save a receipt for an external action. How should the next worker proceed?

<details><summary>Answer & Explanation</summary>

Read the current checkpoint and reconcile the intended operation ID with the downstream system or stable receipt store. Resume confirmed work. Retry an uncertain effect only under an idempotent contract using the same key or under explicit recovery rules. Where neither applies, park the job for review with the evidence needed to investigate.

</details>
