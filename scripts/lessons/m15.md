## 1. The Mental Model

A production agent is a workflow whose quality depends on which actions it takes, what evidence it uses, and how it recovers. A final answer can look correct even when it followed the wrong path, consumed too many tokens, selected an out-of-scope tool, or repeated an external effect. Evaluation-driven development turns those expectations into observable checks before changing prompts, models, or orchestration.

Think of a freight terminal with acceptance tests and live operations. Before a new conveyor opens, inspectors verify that each kind of parcel takes the correct path and stops safely when a sensor fails. During operation, dispatchers monitor queue age, throughput, and exceptions. A shipment ID lets them reconstruct what happened to an individual parcel. Production agent teams need the same three things: pre-release behavior checks, runtime signals, and evidence for individual runs.

| Measure | Primary question | Example evidence |
| --- | --- | --- |
| Tool unit test | Does the business operation handle predictable inputs? | Strict schema, permitted scope, deterministic reply, invariant checks |
| Trajectory evaluation | Did the run follow a permissible path? | Required evidence sourced, allowed tools, bounded retries, approved transition |
| Answer evaluation | Is the result useful and grounded? | Correct claims, required information, evidence citations, appropriate uncertainty |
| Deployment check | Can work survive process and network interruptions? | Durable state, delivery replay, shutdown behavior, stable receipts |
| Runtime signal | Is production meeting quality and reliability goals? | p95 end-to-end latency, queue age, tokens per success, bounded loops |

The goal is a release system with known limits. Put exact rules in deterministic validators. Use a human calibration set and optional LLM judges for qualities requiring judgment. Operate long-lived runs as durable jobs with distinct ownership of task state and business effects.

### Building evaluations that diagnose regressions

Create cases before modifying the system. Each case has a stable ID, version, input, expected behavior, fixture dependencies, and relevant tags. For a travel eligibility request, the expected behavior can require checking the applicable policy date and grounding the response in an approved record. Hard cases might require escalation on contradictory rules. State what alternatives are permissible so the evaluator accepts valid plans with different tool ordering when those operations commute.

Record a **trajectory** as observable events: tool call proposals, validated arguments, authorization results, tool outcomes, retry decisions, and final state. Private model reasoning is unnecessary. Exact order is appropriate where it matters, such as approval preceding an effect. Otherwise use invariants: include a particular evidence lookup, use one of two permitted data sources, never call an unrelated tool, and finish within a bounded number of steps.

Think in layers:

1. A tool unit test replaces dependencies with fixtures and checks inputs, outputs, validation failures, and idempotency. These checks are inexpensive and deterministic.
2. An integration evaluation uses real adapters against controlled dependencies and examines the observed event sequence. Inject failures such as transient provider errors and lost responses.
3. An end-to-end evaluation runs realistic requests through the release candidate with a pinned model, prompt, fixture version, and execution budget. Compare against the deployed baseline on identical cases.
4. An online observation compares production behavior across version cohorts based on telemetry and reviewed samples. Retain only what is necessary, with authorization and retention limits.

Do not decide a release by aggregate pass rate alone. Slice by task type, ambiguity, input length, workflow completion, dependency failure, and applicable policy requirements. If a category has only a few cases, report counts and treat its score as uncertain. A release may need zero observed policy failures on a set of hard checks and a separate threshold for judged answer quality. Zero observed failures in a finite test set does not prove zero production risk.

### Using an LLM judge without handing it the release

An LLM judge applies an explicit rubric to evidence and a candidate response. Give it only inputs required by the rubric, a reference answer when useful, and clear criteria with positive and negative anchors. For grounding, ask which claims are supported by identified evidence, and allow an uncertainty verdict. Validate judge output against a small schema and retain the rubric and judge version along with the result.

Compare the judge against human decisions on held-out cases. Inspect disagreements by category rather than only the overall agreement rate. Test for verbosity preference and positional bias by reversing order when the comparison is pairwise. Grade candidate text as data. Send judge failures and borderline, high-consequence cases to manual review. Keep deterministic authorization and safety gates separate from a model's judgment about answer quality.

A CI gate should freeze the dataset version and record the tested commit and dependency versions. Small threshold changes near a noisy score invite inconsistent merges. Use repeated runs or confidence intervals when variance matters, and define an explicit policy for flaky cases. Do not retry a failed evaluation until it happens to pass. Rerun according to a fixed policy and retain the raw outcomes. Build an inexpensive deterministic suite for every commit and a slower model-backed regression suite on selected candidate changes or a scheduled run.

### Deploying durable jobs

An HTTP request that waits for a long model workflow ties up API resources and makes client disconnect a reliability issue. Instead, persist a job and return an accepted status with a job identifier and status URL. Use a transaction to record the job and an **outbox** entry. An outbox publisher retries sending the queue notification without requiring the client to submit again. Design consumers for at-least-once delivery.

**Visibility lease:** A worker receiving a message usually gets an interval during which other workers do not receive it. The lease can expire during slow calls. Renew it within an overall timeout where the queue supports that model. Because workers can overlap after expiration, use conditional checkpoints and stable effect IDs. If the lease is lost and stopping safely is possible, stop rather than proceeding with stale ownership.

**Acknowledgment:** Acknowledge after the durable outcome or a documented durable intermediate checkpoint. If a worker exits between recording the outcome and acknowledgment, the next worker should find that outcome and acknowledge without redoing work. If it exits between submitting a side effect and learning the result, the next worker must reconcile using the stable key. Keep a dead-letter route for irrecoverable jobs and use controlled redrive that retains previous identifiers.

**Concurrency:** An async worker can await many remote calls, but downstream pools and quotas remain finite. Set a concurrent task maximum and per-dependency caps. CPU-heavy transformation needs its own bounded process or specialized worker so it cannot block the event loop. Preserve a total per-run deadline separate from request timeouts and queue retries. Record cancellation as a durable request that the worker checks at safe boundaries.

**Kubernetes workload:** For a continuously consuming queue, a Deployment normally operates worker pods and replaces failures during rolling updates. A Job fits a bounded batch or one-off worker and has different retry and completion behavior. Set requests and limits based on observed usage. Scale workers from queue backlog, queue age, or another measured demand signal with a maximum consistent with provider quotas. Readiness for new work should reflect initialized dependencies and the ability to accept more leases. Liveness should check a stuck process without treating a temporary provider outage as a fatal worker fault.

On termination, stop accepting new work, pause renewal or drain active leases according to your shutdown contract, and persist progress within the pod grace period. If a workflow cannot finish within that period, ensure it can be retried from a stable checkpoint and avoid acknowledging incomplete work. Version checkpoint readers for rolling upgrades so a new worker can resume older jobs.

### Connecting telemetry to decisions

Create spans around queue wait, model inference, tool execution, and the job lifecycle. Propagate trace context over the queue using metadata appropriate to the queue library. For delayed or batched work, span links may be more accurate than extending one parent span indefinitely. Use the OpenTelemetry GenAI conventions implemented by your instrumentation version for operation, model, token usage, and error fields. Pin the convention version since GenAI attributes and opt-in content capture can change. Record only allowed fields, scrub secrets and personal data, and make sensitive content capture explicit.

Track queue depth and age, time per task, task outcomes, active workers, retry cause, token usage, and goal-specific rates. Do not confuse queue time with processing time. A p95 for model inference can look healthy while queue age pushes end-to-end latency past the target. Prometheus counters measure totals; histogram buckets let you estimate percentiles across pods. Use bounded labels such as workflow, model, or outcome. Store job IDs and individual traces in a trace store with access controls rather than publishing them as metric labels.

Use Grafana panels for queue wait, processing duration, terminal outcomes, and burn rate together. LangSmith can organize traces, datasets, and experiment comparisons. Consider data retention and isolation if using a hosted tool. A repeated-loop alert should measure a real mechanism, such as budget-exhausted runs, repeated identical validated calls, or excessive step counts with no checkpoint advances. Alert on a sustained problem using traffic floors and pair it with a safe action, such as disabling a problematic route or falling back to a bounded alternative.

## 3. Complete Command, Query & Python Syntax Reference

### Assert events and ordering directly

~~~python
def allowed_path(events: list[str], max_tools: int = 3) -> bool:
    if "result_committed" not in events or "scope_checked" not in events:
        return False
    if events.index("scope_checked") > events.index("result_committed"):
        return False
    return events.count("tool_called") <= max_tools

print(allowed_path(["scope_checked", "tool_called", "result_committed"]))  # True
print(allowed_path(["tool_called", "result_committed"]))  # False
~~~

The function takes an ordered list of observed event types and a maximum count. The membership checks avoid searching for missing elements. The index comparison illustrates ordering, and the count bounds tool calls. For production, associate authorization with each individual call ID and check authorization precedes the corresponding operation. The test sample uses one operation to keep the rule readable.

### Compare latency across workers

~~~promql
histogram_quantile(
  0.95,
  sum by (le, workflow) (rate(agent_run_duration_seconds_bucket[5m]))
)
~~~

`agent_run_duration_seconds_bucket` is a classic cumulative histogram series, in this case measuring full run duration including queue wait. `[5m]` is the time range over which `rate` estimates per-second growth, and handles counter resets. `sum by (le, workflow)` merges pods while retaining the cumulative bucket boundary and workflow. `histogram_quantile(0.95, ...)` estimates the duration at or below which 95% of observations fall for each workflow. Choose bucket boundaries around your service objectives to reduce interpolation error. Avoid averaging separately calculated pod percentiles. Verify low-volume windows with the associated observation counts.

For token use per success, compare a rate of total recorded consumed tokens with the matched rate of successful runs over a longer window. Use matching boundaries and explain lag since tokens can be charged before a run reaches its final state. If successful run rate is essentially zero, report the ratio as unavailable and alert separately on successful completions. Count or flag provider calls with missing usage records.

### Check the worker rollout and targeted logs

~~~bash
kubectl rollout status deployment/agent-worker --namespace curriculum --timeout=2m
kubectl logs deployment/agent-worker --namespace curriculum --since=15m --tail=200
~~~

The first command watches rollout of the named Deployment in the `curriculum` namespace for up to two minutes. Kubernetes rollout success verifies deployment conditions, independent of agent task quality. The second command selects a pod from the Deployment and requests recent output, limiting by both time and line count. For exhaustive rollout debugging inspect affected pods individually and correlate with queue and trace evidence. Neither command shows application correctness without a representative completion check.

## 4. End-to-End Real-World Reference Example

### Durable scheduling for a community pottery studio

A studio uses a synthetic queue to draft wheel bookings from a fixed schedule. Every job requires an availability check and may make one simulated booking. This one-file lab models a durable receipt, crashes after persisting it but before queue acknowledgment, then processes a redelivery with a fresh database connection. It also deliberately scores two trajectories, showing that matching output alone is insufficient.

~~~text
pottery-jobs/
  pottery_lab.py     worker, replay demonstration, trajectory evaluator
~~~

Create `pottery_lab.py` with this text.

~~~python
import json
import sqlite3
from contextlib import closing
from pathlib import Path
from tempfile import TemporaryDirectory

class DeliveryLost(Exception):
    """The job outcome was saved before the simulated ack failure."""

def process(db: sqlite3.Connection, job_id: str, lose_ack: bool = False) -> dict:
    record = db.execute(
        "SELECT result FROM receipts WHERE job_id = ?", (job_id,)
    ).fetchone()
    if record:
        return json.loads(record[0])

    result = {
        "slot": "14:30",
        "events": ["availability_checked", "booking_recorded"],
    }

    # Store the simulated local booking and receipt as one unique record.
    with db:
        db.execute(
            "INSERT INTO receipts (job_id, result) VALUES (?, ?) "
            "ON CONFLICT(job_id) DO NOTHING",
            (job_id, json.dumps(result)),
        )
    if lose_ack:
        raise DeliveryLost()
    # A concurrent attempt might have already committed a winning result.
    saved = db.execute(
        "SELECT result FROM receipts WHERE job_id = ?", (job_id,)
    ).fetchone()
    return json.loads(saved[0])

def passes(result: dict) -> bool:
    return result["slot"] == "14:30" and result["events"] == [
        "availability_checked", "booking_recorded"
    ]

with TemporaryDirectory() as folder:
    path = Path(folder) / "jobs.db"
    with closing(sqlite3.connect(path)) as db:
        db.execute("CREATE TABLE receipts (job_id TEXT PRIMARY KEY, result TEXT NOT NULL)")
        try:
            process(db, "wheel-42", lose_ack=True)
        except DeliveryLost:
            print("Receipt persisted before acknowledgment")

    with closing(sqlite3.connect(path)) as fresh:
        restored = process(fresh, "wheel-42")
        total = fresh.execute("SELECT count(*) FROM receipts").fetchone()[0]
        print(f"Receipts: {total}")
        print(f"Replay path valid: {passes(restored)}")
        print(f"Missing check valid: {passes({'slot': '14:30', 'events': ['booking_recorded']})}")
        assert total == 1 and passes(restored)
~~~

Run `python pottery_lab.py` from the folder with the script. Python uses only standard-library modules and creates a disposable database directory. The expected output is:

~~~text
Receipt persisted before acknowledgment
Receipts: 1
Replay path valid: True
Missing check valid: False
~~~

The `TEXT PRIMARY KEY` enforces uniqueness of the logical job ID and `NOT NULL` requires the result field. In the parameterized statements, `?` reserves each value for the driver to bind separately from SQL text. `ON CONFLICT(job_id) DO NOTHING` preserves the first committed record if a concurrent attempt reaches the insert. The connection context commits on success and rolls back on failure, while `closing` closes the connection afterward. The second connection demonstrates persistence across worker sessions. SQLite in this example represents a local effect and receipt in the same transaction. A remote effect requires its own idempotency contract and reconciliation.

Extend the lab with separate fixtures for a fully booked day, a timeout before receiving an acknowledgment, and an independent invalid request. Each fixture should assert whether a receipt should exist and what trajectory is allowed. Then propose a queue adapter exposing receive, renew, and acknowledge with typed delivery handles. Measure queue age, processing time, terminal result and number of attempted actions. Define a trace query that returns the scoped receipt ID without leaking personal booking details.

## 5. Common Pitfalls & Debugging Playbook

### 1. Answer scores improve and the workflow violates a policy

**Symptom:** A new model generates clearer responses but omits an evidence check.

**Root Cause:** Evaluation uses a final-answer rubric without asserting required events before the consequential step.

**Diagnostic:** Compare event traces for the same cases. Check if the candidate omitted a required tool result or used evidence with the wrong version.

**Fix:** Treat the policy as a deterministic trajectory gate and keep answer quality as a separate score.

### 2. A rollout stalls older jobs

**Symptom:** Fresh tasks succeed while previously queued workflows fail soon after pickup.

**Root Cause:** The new worker cannot decode older checkpoints or assumes a new step already ran.

**Diagnostic:** Inspect checkpoint version, current worker version, and the first invalid transition in a failing trace.

**Fix:** Add a compatible versioned reader or migrate checkpoints against recorded fixtures before rolling forward. Pin older workers for draining only when your routing supports it.

### 3. Scaling workers makes latency worse

**Symptom:** More pods launch, provider rate limits increase, and retries extend the queue's oldest age.

**Root Cause:** Global concurrency exceeds an external quota. Each pod obeys a reasonable local limit, but their sum does not.

**Diagnostic:** Graph worker count, active calls, queue age, and rate-limit errors. Compare retry frequency before and after scaling.

**Fix:** Bound worker and per-dependency concurrency with shared quotas or a known maximum. Use budgeted retry with delay and tune scaling to actual completions.

### 4. The token dashboard has gaps or misleading averages

**Symptom:** Failed tasks seem free and latency looks healthy even during backlog.

**Root Cause:** Token metrics are attached only to completions, or the latency series excludes queue wait.

**Diagnostic:** Compare provider usage for attempts with terminal status and count usage-missing spans. Trace submission to worker receive and completion as separate timestamps.

**Fix:** Measure token use at calls, carry missing-usage counts, and publish queue and end-to-end distributions. Aggregate from counters and compatible histogram buckets.

### 5. CI judges disagree on nearly identical results

**Symptom:** The same eligible change alternates between pass and fail across runs.

**Root Cause:** A vague rubric, small sample, unstable reference context, or position bias makes a borderline score random.

**Diagnostic:** Re-score a pinned set including human-calibrated examples, reverse pair order for comparisons, and inspect disagreements by task type.

**Fix:** Clarify rubrics, freeze versions, use deterministic gates for exact conditions, and define a separate path for uncertain comparisons.

1. Define queue ownership, coordination keys, checkpointing, and graceful termination.
2. Terminate a worker mid-case and verify recovery without duplicate decisions.

#### Acceptance Checklist

Concurrent workers on the same logical job cannot commit two recommendations. A failed dependency does not keep a worker lease forever. Simulate a crash after result commit but before acknowledgment and show the next worker reconciles the stored result. Verify progress can resume after a controlled schema upgrade. Observe queue age and retry reasons throughout.

### Project 3: Language Tutor Cost Monitor

1. Choose trace fields, cost and latency metrics, and alerts for abnormal loops.
2. Replay a long synthetic interaction and verify the alert and trace point to its cause.

#### Acceptance Checklist

One long productive interaction and one loop produce distinguishable signals. The alert fires for a sustained reproduction and stays quiet at insufficient traffic. The dashboard shows p95 end-to-end time, successful runs, tokens per success, and time spent in queue. An operator can locate a representative trace without putting user IDs in metric labels.

## 7. Mastery Checkpoint Questions

### Q1. A final answer looks correct but the agent made an inappropriate tool call beforehand. What evaluation catches that?

- A. A token count alone
- B. Only a final-answer judge
- C. Step-level trajectory and tool-policy assertions

<details><summary>Answer & Explanation</summary>

**Answer: C.** The final text can hide unsafe or wasteful intermediate behavior. Evaluate the actions as well as the answer.

</details>

### Q2. A queue redelivers a job after a worker exits before acknowledging it. What should the new worker do?

- A. Resume or reconcile using persisted state and an idempotent operation key
- B. Assume all earlier steps failed
- C. Disable retries globally

<details><summary>Answer & Explanation</summary>

**Answer: A.** Redelivery is normal for at-least-once processing. Persist state and make external effects safe to replay.

</details>

### Q3. The model p95 is flat while end-to-end p95 grows. Which extra signal should you check first?

- A. The number of tokens in the system prompt
- B. Queue wait or oldest pending job age
- C. The longest span name

<details><summary>Answer & Explanation</summary>

**Answer: B.** A growing delay can occur before the worker even calls the model. Split elapsed time into queue, run, and dependency intervals.

</details>

### Q4. What should the release gate do when a quality judge and a deterministic authorization test disagree?

- A. Allow the release if the judge likes the final answer
- B. Rerun until they agree
- C. Enforce the authorization test and report quality separately

<details><summary>Answer & Explanation</summary>

**Answer: C.** Hard policy checks protect behavior that a quality rubric cannot override. A strong answer adds no authority to its trajectory.

</details>

### Q5. Two pods compute their own p95 latencies. How do you get the workflow's p95 across both pods?

- A. Average the two p95 values
- B. Take the slowest pod's p95 as an exact estimate
- C. Aggregate rates of compatible histogram buckets before estimating p95

<details><summary>Answer & Explanation</summary>

**Answer: C.** Percentiles summarize shapes that can differ across pods and request counts. Merge compatible observations through bucket counts and estimate once.

</details>

### Q6. Outline a test for a Kubernetes termination that arrives during a remote write.

<details><summary>Answer & Explanation</summary>

Arrange a controllable remote effect and force termination between request and acknowledgment. Stop taking new work, check that incomplete work remains recoverable, and start a replacement using the prior job and effect IDs. Verify the replacement reconciles the existing effect and records one outcome and no second effect. Inspect a trace or structured events for both attempts.

</details>

### Q7. A CI suite has 96 passing easy cases and 4 failed cases involving conflicting provider evidence. Explain how you would report and gate the result.

<details><summary>Answer & Explanation</summary>

Report the whole score and the conflict slice, which has four failures out of four. Define a hard or separate threshold for the risk-bearing slice, and inspect expected actions and uncertainty handling for those failures. Add representative labeled cases and avoid hiding the concentrated regression in the aggregate.

</details>
