## 1. The Mental Model

Git is an immutable object store with movable references. A commit describes a snapshot and points to its parent history. A branch is a name for a commit, so most apparent “file operations” in Git actually update one of three places: the working tree, the index, or a ref.

Think of Git like publishing editions. The working tree is your desk, the index is the exact package of pages for the next edition, and a commit is the published edition plus its history. Review the package before publishing it.

| Operation | What it updates |
| --- | --- |
| Stage | Copies path content into the index |
| Commit | Creates objects for the staged snapshot and advances the current branch |
| Merge | Combines histories using a common ancestor |
| Rebase | Replays changes on a new base and creates new commit IDs |

Trunk-based teams integrate small changes frequently under CI. GitFlow uses longer-lived integration and release branches for parallel release lines, with additional merge and coordination costs. Choose branch policy around deployment and review needs.

### A commit is an evidence boundary

When a code change breaks a build, “what changed?” has a precise answer only after you identify two snapshots and the environment used to run them. Git lets you compute the difference between snapshots, find when a property stopped holding, and preserve the diagnosis for other engineers. Keep changes reviewable so a snapshot has an explainable purpose and a comparison tests a meaningful claim.

Treat integration as three related decisions. The **commit** selects files and records intent. The **pull request** makes the comparison visible for review. The **branch policy and CI** decide when the comparison can become part of shared history. A successful local test verifies your working tree. A successful CI run verifies the ref checked out by the runner, which may be the proposed merge result. Both are useful, but they certify different trees if you failed to stage a fix or the base branch moved.

| Team situation | Useful integration model | Trade-off to manage |
| --- | --- | --- |
| One regularly deployed service | Short branches against a protected trunk | Keep changes small and use feature flags to separate merge from rollout. |
| Several maintained product versions | Trunk with maintenance branches from released tags | Decide which fixes are eligible for backporting and test each supported branch. |
| Scheduled releases with parallel stabilization | A release branch or a GitFlow-style split | Extra branches incur cross-branch testing, release coordination, and backport conflicts. |

### Choose the history operation from the problem

If you need an exact copy of a released snapshot, check out its tag or full object ID in a dedicated lab directory. If you need to undo behavior already shared with others, a revert commit records the correction without invalidating anyone's base. If you are organizing private unpublished commits for review, an interactive rebase can combine noisy steps into auditable changes. When integrating independent lines of shared work, preserve each author's history with a merge if the repository’s policy and release requirements expect it.

## 2. Core Architecture & How It Works Under the Hood

```text
 working tree       index            object database
 +-----------+      +-----------+    +----------------------------+
 | edits     | add  | path->ID  |    | blob: content              |
 | new files | ---> | mode      | -> | tree: named blobs/subtrees |
 +-----------+      +-----------+    | commit: tree + parent(s)  |
                                      +------------^---------------+
                                                   |
 HEAD --> refs/heads/topic ------------------------+
```

1. Git hashes content into immutable objects. Blobs have content, trees attach names and modes, and commits reference a tree and parents.
2. The index tracks the staged path and object ID. Compare it to the working tree and HEAD separately when you review changes.
3. Ref updates move branch tips. A merge can fast-forward if one side is already an ancestor, or create a commit with two parents after a three-way merge.
4. Rebasing replays commits and assigns new IDs because parents change. Coordinate any rewrite of a shared branch before publishing it.
5. A pull request reviews a comparison between tips, while CI verifies a chosen ref. A small PR with explicit tests and a narrow scope makes review and conflict resolution easier.

### Object identity and reachable history

A blob stores bytes and has no filename. A tree attaches names, modes, and object IDs to the entries of a directory. A commit points to the root tree, zero or more parents, and metadata including author, committer, times, and message. Unchanged content can reuse an object, so the snapshot model does not require storing another full copy of the project on every commit. The displayed patch is calculated by comparing snapshots. Git can also pack objects and use deltas as a storage optimization. Those physical deltas do not change how a commit describes its tree.

An object ID depends on the content and type of the object. Changing one file replaces its blob and changes trees along the path to it. A same-content commit can still get a different ID because the parent, message, or other commit fields changed. A merge commit usually has two parents, where the first is the branch you were on and the second is the branch you merged. A fast-forward only moves a ref because the target already includes the old tip as an ancestor.

Objects still reachable through branches, tags, and other retained references remain in the store. A locally deleted branch name does not immediately delete its commits. A reflog records recent movements of refs in that repository and may help recover an earlier tip, subject to retention. Create a recovery ref as soon as you identify the right commit. Remember that reflogs are local observations and do not serve as a backup of every clone or remote.

### Local, remote-tracking, and remote refs

An ordinary local branch is writable in your checkout. A remote-tracking ref such as `origin/main` records what you last fetched from a remote. The branch named `main` on the remote is a separate ref on another Git repository. Until you fetch, the local view may be stale. A normal push advances the remote ref if permissions and non-fast-forward rules allow it. If another change reached the remote first, fetch and integrate the new history rather than replacing it.

`git pull` typically fetches and then performs the configured integration action. Specify the desired integration strategy when following a team policy. An explicit fetch followed by inspection is easier to reason about if the branch state is unfamiliar. An “ahead/behind” status is a graph comparison to the local upstream ref. It is not an online check.

### Three-way integration and the index

When both branches modified the same area, Git compares their trees to a merge base. It may still merge non-overlapping edits cleanly, while encountering a content conflict where the edits overlap or have incompatible tree changes. The index represents an unresolved path with stage 1 for the common base, stage 2 for the current side, and stage 3 for the incoming side. A deletion may mean a stage is absent. Editing a conflicted working file does not resolve the index by itself. Stage the resolved file or expected removal to record your decision.

There is also a **semantic conflict** when Git merges distinct lines but the resulting behavior is inconsistent. Imagine one change broadening what counts as a valid result while another computes billing from the old range. A clean merge still needs regression tests. Write tests for the combined contract and pay particular attention to joined behavior across modules and schema changes.

### What hosted CI actually does

A hosted CI job receives an event. The workflow provisions a runner, checks out a specific ref, installs declared dependencies, runs checks, and reports status. For many pull request workflows the checked-out commit is GitHub's test merge ref, while a push workflow checks the pushed commit. Confirm the SHA and event type before comparing results. A job can also build an artifact, such as a wheel or static bundle. Build once for a deployment stage and retain the producing revision and artifact digest so you can reproduce or restore it.

Set job-specific permissions and default to read-only for tests. Treat pull request code and event text as untrusted. Keep tests from untrusted PRs away from deployment credentials. Store release credentials behind environment approvals or an equivalent least-privilege release policy. Repository branch protection or rulesets enforce the review and required-job policy even when a contributor's local hook passes.

## 3. Complete Command, Query & Python Syntax Reference (Progressive)

### Inspect and stage deliberately

```bash
git status --short --branch
git diff
git diff --staged
git add -p
git cat-file -t HEAD
git cat-file -p HEAD
git log --graph --oneline --all
```

- `--short` condenses status, with the index in the first column and the working tree in the second. `--branch` adds branch tracking information.
- `git diff` compares working files to the index. `--staged` compares the index to HEAD. `git add -p` prompts per hunk.
- `cat-file -t` prints an object type, and `-p` renders its content. `HEAD` resolves through your current branch or to the checked-out commit in detached mode.
- `log --graph --oneline --all` shows topology, compact commit summaries, and refs outside the current branch.
- A typical `.gitignore` excludes `.venv/`, `__pycache__/`, and local secret files. Ignore rules affect untracked files. If a real secret was committed, revoke it and coordinate removal as an incident.

### Integrate and resolve conflicts

```bash
git fetch origin
git switch -c topic origin/main
git merge --no-ff other-topic
git rebase -i HEAD~3
git diff --name-only --diff-filter=U
```

- `fetch origin` updates remote-tracking refs. `switch -c topic origin/main` creates a branch named topic at the fetched commit and checks it out.
- `merge --no-ff` asks for a merge commit even when a fast-forward is possible. Use it when the project wants explicit integration points.
- `rebase -i HEAD~3` opens a todo list for the three latest commits on a linear branch. Use `pick` to keep, `reword` to edit a message, or `fixup` to fold a commit without its message.
- `--name-only --diff-filter=U` lists paths with unresolved index entries. Review both sides, write the integrated behavior, stage specific paths, and continue the active merge or rebase. Re-run tests and review the staged diff before continuing.

### Inspect the exact staged and committed objects

```bash
git ls-files --stage -- fees.py
git show HEAD:fees.py
git diff --cached -- fees.py
git check-ignore -v -- .venv/pyvenv.cfg
```

`ls-files --stage` prints the index mode, object ID, stage, and path. Stage `0` is a resolved entry. `show HEAD:fees.py` reads the file from the tree recorded at `HEAD` with no working-tree modifications, and `diff --cached` is synonymous with `--staged`. `--` separates arguments from paths. `check-ignore -v` prints the source file, line number, and matching pattern for an ignored path. A tracked entry will not normally be reported as ignored unless you ask the command to disregard the index. Expect the lab’s ignored virtual-environment path to match the `.venv/` rule.

When `git status --short` reports `MM fees.py`, the first letter means the index differs from HEAD and the second means the working file differs from the index. Stage only the version you intend after inspecting both diffs. To remove an accidental inclusion from the next snapshot while retaining working edits, `git restore --staged -- fees.py` copies the HEAD version of that entry to the index. A command that restores the working tree has different consequences, so distinguish the destination before executing it.

### Inspect divergence before integrating

```bash
git fetch origin
git log --left-right --oneline HEAD...origin/main
git diff --stat origin/main...HEAD
git merge-base HEAD origin/main
```

`log` with the symmetric range `A...B` lists commits reachable from either side but not both. `--left-right` marks which side contributed each commit. For `git diff A...B`, the same punctuation has a different meaning: it compares the merge base of A and B to B. `--stat` summarizes file changes rather than printing each hunk. `merge-base` prints a best common ancestor in ordinary diverged history. A new branch with one commit based on current main should show one commit on the local side and the diff should cover only the proposed change.

Use `git merge --ff-only origin/main` for fast-forward synchronization from the fetched ref when you expect your current branch to be its ancestor. The command refuses if the histories need integration. If project policy accepts rebasing a short, unpublished branch, `git rebase origin/main` replays your commits on the fetched base. Run the tests after the rewrite. Share the new tip explicitly and avoid rewriting a branch collaborators already use without coordination.

### Recover and locate a regression

```bash
git reflog --date=iso -n 10
git branch recovered "$reviewed_commit"
git show --stat recovered
```

`reflog --date=iso` shows local ref movement timestamps and `-n 10` limits the display. Set `reviewed_commit` to the verified object ID to recover. `branch recovered` creates a new pointer without altering your files or existing branch names. `show --stat` displays the commit and file statistics. A recovery ref gives you time to inspect the older snapshot before deciding how to integrate it.

When a regression has a known good and bad commit, `git bisect` performs a binary search over relevant history. Start with `git bisect start`, mark `git bisect bad <bad-commit>` and `git bisect good <good-commit>`, then run the same narrow test on each checked-out revision. Mark each reproducible result good or bad. Use `git bisect skip` when the revision cannot be tested, and `git bisect reset` to end the search and return to the original checkout. For `git bisect run <test-command>`, use a script with stable outcomes: zero is good, expected test failure uses a supported nonzero exit status, and 125 skips an untestable revision. Pin the environment across the search so a dependency change is not mistaken for a source regression.

### Revert, cherry-pick, and tags

`git revert <published-commit>` records a new commit that reverses an ordinary single-parent change relative to current history. If later work depends on it, inspect the proposed inverse and test the new behavior before sharing. `git cherry-pick <reviewed-commit>` re-applies a selected change as a new commit, often for a backport. A successful cherry-pick into a maintenance branch still requires tests in the maintenance context. An annotated tag such as `git tag -a v1.2.0 -m "Release 1.2.0"` stores release metadata and references the current commit. `-a` selects an annotated tag and `-m` provides its message. Treat shared release tags as stable names and verify their target before release.

## 4. End-to-End Real-World Reference Example (Python-Centric)

A bike-share reporting team is changing its trip fee policy. Two branches will modify the same function, so the final test should demonstrate that both policy changes made it into the merge.

```text
trip-fees/
  .gitignore
  fees.py
  test_fees.py
  .github/workflows/ci.yml
```

**`fees.py`**

```python
def trip_fee(minutes: int, member: bool = False) -> int:
    """Return the trip fee in cents."""
    return minutes * 25
```

**`test_fees.py`**

```python
import unittest

from fees import trip_fee


class FeeTests(unittest.TestCase):
    def test_regular_trip(self) -> None:
        self.assertEqual(trip_fee(4), 100)


if __name__ == "__main__":
    unittest.main()
```

**`.gitignore`**

```gitignore
.venv/
__pycache__/
.env
```

**`.github/workflows/ci.yml`**

```yaml
name: Trip fee tests
on: [push, pull_request]
permissions:
  contents: read
jobs:
  tests:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
      - run: python -m unittest -v
```

The workflow runs on pushes and pull requests, checks out the event ref, selects Python 3.12, and runs discovery through the standard library. The token needs repository read access only.

In a new disposable directory with those files, run the commands below. `git init -b main` names the initial branch. Set a lab-only identity if Git has no identity configured. `git add .` stages the lab files, and `commit -m` supplies the commit message.

```bash
git init -b main
git config user.name "Lab Learner"
git config user.email "learner@example.com"
git add .
git commit -m "Add trip fee calculation and tests"
git switch -c zero-floor
```

On `zero-floor`, change the return expression to `max(0, minutes) * 25`, stage `fees.py` and commit. Switch to `main` and then create `member-price` from it. On that branch, change the return expression to `minutes * (20 if member else 25)`, stage and commit.

```bash
git merge zero-floor
git diff --name-only --diff-filter=U
```

Expect a conflict in `fees.py`. Retain both policies in one expression: `max(0, minutes) * (20 if member else 25)`. Add tests that verify a four-minute member trip is 80 cents and a negative-duration trip is zero. Stage `fees.py` and `test_fees.py`, run `python3 -m unittest -v`, then run `git commit -m "Combine minimum duration and member pricing"`. Expect three passing tests and a merge commit with two parents in `git log --graph --oneline --all`. In a shared repo, put the resolved branch into a PR and explain the two guarantees and the tests.

### Inspect the three snapshots before resolving

Before editing the conflicted file in the disposable repository, run `git show :1:fees.py`, `git show :2:fees.py`, and `git show :3:fees.py`. The colon syntax selects an index stage for that path. You should see the original regular fare in stage one, the membership price in stage two, and the zero floor in stage three. Write down the independent guarantees. Choosing one side blindly loses the other guarantee even if the file has valid Python.

After staging the resolution, rerun `git diff --name-only --diff-filter=U`. The list should be empty. Review the staged diff relative to the current branch and read `git status` to confirm a merge is still in progress and the index is ready for commit. `git diff --cached --check` tests staged patch whitespace and conflict marker issues, while unit tests verify the pricing behavior. After committing, `git rev-list --parents -n 1 HEAD` prints the merge commit followed by its two parents. `--parents` includes parent identifiers, `-n 1` limits output to one commit, and `HEAD` chooses the tip. Compare those identifiers with each branch before and after integration.

### Read a CI run as evidence

The workflow name labels the pipeline. `on` selects pushes and pull requests as event sources. `permissions.contents: read` gives the runner enough privilege to obtain the repository. The `tests` job uses a hosted Linux runner and sequential action or shell steps. The checkout step obtains the event ref and the Python action selects the runtime. `python -m unittest -v` invokes test discovery with method names shown in its result. Compare that output with the three expected cases. For a real project, keep an explicit dependencies file or lock, require the relevant job in branch policy, and use an approved action pinning policy.

To practice review, produce a short PR description containing the changed pricing contract, compatibility impact, and exact validation. Name all three test cases and explain what a failure means. Then ask a reviewer to reproduce from a clean checkout of the reviewed commit. The test protects future refactoring only if it encodes both branch requirements independently of the implementation.

## 5. Common Pitfalls & Debugging Playbook

### 1. The commit misses a recent edit

**Symptom:** The working file is correct, but the committed version is old.

**Root Cause:** The edit was made after staging. A commit uses the index.

**Diagnostic:** Compare `git diff` with `git diff --staged`.

**Fix:** Re-stage the specific hunk and review the staged diff before committing.

### 2. A tracked secret remains visible after adding an ignore rule

**Symptom:** A secret file still appears in Git status or history.

**Root Cause:** Ignore rules apply to untracked paths. Existing commits still reference their blobs.

**Diagnostic:** Use `git ls-files -- .env` to check the index and inspect which commits introduced the path without printing its contents.

**Fix:** Revoke the exposed credential, coordinate history cleanup if needed, and keep the path untracked going forward.

### 3. Rebase conflicts seem to reverse ours and theirs

**Symptom:** A blanket conflict choice discards your patch.

**Root Cause:** During a rebase, the current side is the rebased base and already-replayed changes. The incoming side is the patch being replayed.

**Diagnostic:** Inspect `git status`, the conflict markers, and `git rebase --show-current-patch`.

**Fix:** Resolve the intended behavior line by line, stage the result, run tests, and continue the rebase.

### 4. CI passes locally and fails on the pull request

**Symptom:** The runner cannot import a package or find a file.

**Root Cause:** The runner starts from a clean checkout, or tests a different ref and runtime version.

**Diagnostic:** Check the failed job's SHA, selected Python version, cwd, and the exact command in its logs.

**Fix:** Use a pinned dependency setup, commit required source and fixtures, and reproduce with the runner's command.

### 5. A push is rejected because the remote advanced

**Symptom:** The server rejects an ordinary push as non-fast-forward after someone else integrated work.

**Root Cause:** The remote branch has a tip that is not an ancestor of the proposed tip. Overwriting it would discard its line of history from that branch.

**Diagnostic:** Fetch the appropriate remote and compare `git log --left-right --oneline HEAD...origin/main` after checking the push target and upstream. Distinguish graph divergence from a separate permissions or required-checks error reported by the server.

**Fix:** Integrate the new commits with a merge or an unpublished-branch rebase according to team policy. Rerun the original verification on the final snapshot and push normally. For a protected branch, submit the reviewed change through the repository’s required PR flow.

## 7. Mastery Checkpoint Questions

### Q1. A developer stages a path, edits it again, and commits. Which contents does the commit include?
- A. The working tree at the instant of commit.
- B. Both versions of the path.
- C. The blob staged in the index.
- D. The latest remote-tracking version.

<details>
<summary>Answer & Explanation</summary>

**Answer: C.** A commit records the index snapshot. Compare the index to the working tree before each commit when a path shows both staged and unstaged changes.

</details>

### Q2. A commit points directly to which object for its top-level snapshot?
- A. A tree.
- B. A branch.
- C. A tag.
- D. A remote URL.

<details>
<summary>Answer & Explanation</summary>

**Answer: A.** A tree maps names and modes to blobs and subtrees. The commit records that tree plus its parents and metadata.

</details>

### Q3. Why does an otherwise unchanged patch usually get a new commit ID after rebasing onto main?
- A. The author always changes.
- B. A commit includes its parent object IDs.
- C. Rebasing converts trees to blobs.
- D. Staging clears the old object database immediately.

<details>
<summary>Answer & Explanation</summary>

**Answer: B.** The parent is part of the commit object. Replaying a patch on a new parent produces a different commit even when the patch itself is identical.

</details>

### Q4. Two branches each contain a commit the other lacks. What information does Git use to combine the edits in a three-way merge?
- A. The branch with the newest author date only.
- B. The staging area and the remote URL only.
- C. Two copies of the current working tree.
- D. Both branch tips and their merge base.

<details>
<summary>Answer & Explanation</summary>

**Answer: D.** Git compares each side to the common base. Overlapping incompatible edits may require a semantic resolution.

</details>

### Q5. A local file is tracked, then its pattern is added to .gitignore. What happens?
- A. The tracked file is removed from history.
- B. The rule applies only once a PR is opened.
- C. The file remains tracked until it is removed from the index explicitly.
- D. Status hides all edits to it permanently.

<details>
<summary>Answer & Explanation</summary>

**Answer: C.** Ignore rules govern untracked file discovery. They do not remove index entries or the objects referenced by older commits.

</details>

### Q6. A service team is adopting short-lived branches. Describe how a pull request, the index, and CI together keep a developer’s local edits from leaking into the shared release.

<details>
<summary>Answer & Explanation</summary>

Stage the intended hunks and inspect the staged diff, then commit that snapshot to a topic branch. Review the resulting comparison to the target branch. Run CI from a clean checkout of the PR ref to verify the committed snapshot independently of local files, and integrate only the reviewed, passing result.

</details>

### Q7. The remote main branch changed after your last fetch. The server now rejects your push as non-fast-forward. Which recovery preserves collaborators’ work?

- A. Fetch and inspect the graph, integrate the current remote tip, retest, and push through the normal policy.
- B. Delete the remote branch and create it with your local commit.
- C. Rerun the same push until the server accepts it.
- D. Remove local remote-tracking refs and retry without fetching.

<details>
<summary>Answer & Explanation</summary>

**Answer: A.** Fetch gives you current evidence and integration keeps both lines of history. Tests should run against the new combined snapshot since it may differ from the one you previously verified.

</details>

### Q8. A file has an automatic merge with no conflict markers, but a regression appears when the merged branches run together. Describe a reproducible investigation.

<details>
<summary>Answer & Explanation</summary>

Start by confirming the exact failing revision and test environment. Find the merge parents and their base, reproduce the failure on the merge, and run the narrow test against both parents to distinguish a pre-existing defect from a semantic interaction. Identify the previously independent assumptions, encode the combined contract in a regression test, and submit the fix as a reviewable commit.

</details>

### Review the commands by the evidence they produce

| Question | Inspect |
| --- | --- |
| What will my next commit contain? | The staged diff and the index entries for the changed paths. |
| Which work is reachable on each side? | The commit graph after updating the appropriate remote-tracking refs. |
| What did each side contribute to a conflict? | The merge base, both changed trees, and the conflict stages in the index. |

| Can a change be safely undone? | The prior snapshot, dependent changes, and a new passing revert if the history is shared. |

For practice, begin with a clean lab checkout and predict the output of each inspection before running it. If your mental model differs from the output, identify the tree or ref that you actually asked Git to inspect. Most confusion comes from comparing the right files in the wrong places.
