## 1. The Mental Model

PostgreSQL coordinates durable facts across independent writers. Start with the fact that needs to stay true when two requests arrive together, then choose the tables, constraints, and transaction boundary that keep it true. Search indexes provide access paths to those facts at a cost in storage, write work, and maintenance.

Think of a records office. The register is authoritative, the same filing rules apply at every counter, and specialist catalogues help clerks find a subset of entries. An approximate catalogue finds related subjects quickly, while a constraint in the register enforces a precise structural rule.

### Model identity, relationships, and history

Imagine tracking emergency generator inspections. An asset has a stable ID and an owning facility. An inspection belongs to one asset and records a time, outcome, inspector, and checklist version. Separate the entities and use foreign keys for ownership. Copying the facility address onto every inspection creates contradictions after a move. If you need the address at inspection time for compliance, name that field as a historical snapshot and specify when it becomes immutable.

- **First normal form** gives each position one value at the granularity the application queries and updates. If parts on an inspection require independent quantities and approvals, model them as rows. Attributes belonging to one small value object can remain together.
- **Second normal form** asks whether an attribute depends on the entire composite key. In a table keyed by inspection and part, the timestamp belongs to the inspection, while the inspected quantity depends on the pair.
- **Third normal form** removes dependencies between non-key facts. Store a facility zone on the facility, then join it when reading assets. Denormalize deliberately for a measured access path and name the writer responsible for keeping copies current.
- A **primary key** gives a row identity. **Unique constraints** express alternate identities such as a device serial within a facility. **Foreign keys** tie records together and require a deletion policy. **Check constraints** enforce row-local rules such as a nonnegative reading. For invariants among multiple rows or tables, consider uniqueness, exclusion constraints, explicit locking, or Serializable.

A typed column fits required data that is frequently queried, joined, or constrained. **JSONB** carries sparse metadata whose keys differ by instrument model. A document still needs validation and a policy for schema evolution. Decide which keys participate in search and promote a field to a typed column when its role becomes central.

Search requirements deserve separate design. Full-text search uses terms, normalization, and rank. Vector retrieval uses learned similarity to find passages whose wording differs from a query. A query for “power switchover” can find a passage mentioning load transfer. An exact serial or safety code often deserves a normalized lookup field. Regardless of ranking method, keep document identity, revision, and access policy explicit.

| Need | Primary mechanism | Important limitation |
| --- | --- | --- |
| Reserve an exclusive asset | Constraint plus transaction | Reading available stock does not claim it |
| Page recent inspections | Ordered B-tree | Include time and a stable tie-breaker |
| Find entries tagged urgent | JSONB containment with GIN | Verify operator class support |
| Find an uncommon exact part code | Normalized code field | Natural-language dictionaries may transform text |
| Prioritize conceptually similar passages | Vector distance, optionally accelerated by HNSW | Quality depends on the encoder, metric, and corpus |

## 2. Core Architecture & How It Works Under the Hood

```text
Python service -> bounded connection pool -> PostgreSQL backend/session
                                                   |
                                       parse, rewrite, plan
                                                   |
                                    executor + transaction snapshot
                              +-------------+--------------+--------------+
                              |             |              |              |
                            heap           B-tree         GIN            HNSW
                         row versions   ordered keys   term/JSON keys  vector graph
                              |
                         WAL flushed on durable commit -> later checkpoint
```

### Transactions, snapshots, and locks

A connection hosts a session. A transaction groups work within the session. A snapshot controls visible versions. A row lock coordinates writers while a snapshot determines visibility. **MVCC** keeps historical row versions available while a concurrent reader still needs them. A new committed version becomes visible to later snapshots, and autovacuum eventually reclaims versions beyond the visibility horizon. Long-lived transactions can hold that horizon back, increase table or index size, and make maintenance too slow for the workload.

ACID describes useful runtime commitments. **Atomicity** commits or rolls back a group of operations together. **Consistency** means valid transactions preserve the encoded constraints and business invariants. **Isolation** constrains interactions between concurrent transactions. **Durability** follows the database's configured commit and storage guarantees. The **write-ahead log**, or WAL, records changes before modified data pages reach durable storage. On startup after a crash, PostgreSQL can replay WAL. Replication and backups have separate recovery guarantees. Test restore and failover against a defined maximum tolerable data loss and outage window.

| Isolation mode | Visibility | Consequence |
| --- | --- | --- |
| Read Committed | Fresh snapshot per statement | Repeat reads can see different committed data |
| Repeatable Read | Snapshot from first snapshot-taking statement | Stable reads still permit some anomalies across rows |
| Serializable | Transaction snapshot and checks on dependency patterns | The server can abort one transaction to preserve a serializable outcome |

For a write-skew example, imagine two responders reading that both are on call and separately taking themselves off duty. Each updates a different row, so each individual update can succeed against the shared snapshot. Enforce coverage by locking the shift row before checking coverage or by running at Serializable with bounded retries. Retrying only the last statement preserves the old decision. Retry the whole transaction with a fresh snapshot. For work that triggers an external effect, record an outbox entry in the same transaction and deliver later with a stable operation identity. This keeps a retry inside the database from sending an extra notification.

### How query plans and indexes work

The planner estimates result sizes and weighs scans, joins, ordering, and other operators. Cost units are planner estimates. Runtime duration and buffer accesses come from the executor. A sequential scan can win for a small table or a broad query because visiting most heap pages through separate index lookups may incur extra work.

A **B-tree** organizes entries in key order. With an index over facility, timestamp, and ID, equality on facility narrows the key range and the index can serve timestamp order directly. The ID breaks ties. Index-only scans rely on heap page visibility information, so frequently updated tables can still need heap visits. A **GIN** inverted index maps terms or components to matching rows. It fits full-text search or JSON component predicates and adds storage and update costs. The default JSONB GIN operator class covers more operators, including key existence. The path-oriented class covers narrower containment and supported JSON path predicates. Pick the class after listing your query operators.

### Choose distance and compare the search paths

An encoder turns a passage into a vector of fixed dimensions. Query and passage vectors must come from compatible embeddings. **Cosine distance** measures directional difference and typically works well when the model was trained for cosine similarity. **L2 distance** measures Euclidean separation and reacts to magnitude. Unit normalization can make these two distances produce equivalent rankings. It cannot correct a mismatch between encoders, and a zero vector has no direction. Track model version, dimensions, normalization, and metric.

Exact retrieval scores every eligible vector and supplies a comparison baseline. **HNSW** builds a multilayer neighborhood graph, with coarse navigation above dense local connections. Search expands around nearby nodes until it reaches its candidate budget. Graph build settings affect memory, build time, and connectivity. The query's search-effort setting trades latency for recall. A selective tenant or access filter can be applied after the graph generates candidates, leaving fewer authorized results than requested. Compare results to exact search under the same filter. For small tenant slices exact search can be both fast and accurate. Other options include supported iterative scans, partitioning, or selective partial indexes with suitable query predicates.

In **hybrid retrieval**, lexical and vector search give separate candidate lists. Raw scores use different scales. Reciprocal rank fusion uses one divided by a constant plus rank for each candidate's contribution. With constant 60, a passage ranked first by text and third by vectors scores roughly 0.0323. A passage ranked first on only one list scores about 0.0164. Evaluate exact codes, paraphrases, short queries, near-duplicates, and restricted access scopes. Measure latency, recall, and result count before and after changing index settings.

## 3. Complete Command, Query & Python Syntax Reference

### Express the invariant in the write

```sql
UPDATE inventory
   SET available = available - 1
 WHERE sku = $1 AND available > 0
 RETURNING available;
```

This assumes a unique SKU and a nonnegative inventory constraint. The placeholder is a prepared SQL parameter. The SKU selects the record. The stock predicate makes the update conditional and can be rechecked after waiting on another writer at Read Committed. The returning clause reads the new state in the same statement. If two sessions claim the last unit, one returns zero and the other receives no row. Put the reservation entry and the stock change in one transaction. For operations that lock several records, keep lock order consistent to reduce deadlocks.

### Match indexes to queries and measure the plan

```sql
CREATE INDEX inspections_recent ON inspections (facility_id, inspected_at DESC, id DESC);
CREATE INDEX inspections_tags ON inspections USING gin (attributes jsonb_path_ops);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, inspected_at
FROM inspections
WHERE facility_id = 7
ORDER BY inspected_at DESC, id DESC
LIMIT 20;
```

The first index follows the equality filter with the sort keys. The second can serve a containment predicate such as **attributes @> '{"severity":"urgent"}'::jsonb**, where the cast types the comparison object. **ANALYZE** actually runs the statement and includes runtime rows, timing, and loop counts. **BUFFERS** reports shared cache hits and reads as well as temporary spill. Use a disposable schema for write experiments. Check whether the chosen scan produces the desired ordering before sorting. Approximate work for a repeated node by multiplying actual rows per loop by loop count. If estimates are far from actual rows, check statistics freshness and the correlation between filter columns. Validate with a realistic data distribution.

### Psycopg 3 async integration

```python
import psycopg

async def reserve(dsn: str, sku: str) -> int | None:
    async with await psycopg.AsyncConnection.connect(dsn) as conn:
        async with conn.cursor() as cur:
            await cur.execute(
                "UPDATE inventory SET available = available - 1 "
                "WHERE sku = %s AND available > 0 RETURNING available",
                (sku,),
            )
            row = await cur.fetchone()
    return None if row is None else row[0]
```

Psycopg's value placeholder is **%s**, and the one-item tuple has a trailing comma. The driver sends values separately. Execution and result waits are asynchronous. Fetch one returns a row tuple or **None**. Leaving the connection context commits on success, rolls back on error, and closes the connection. At starting stock one, two sequential calls for the same SKU return zero, then **None**. In a service, create a bounded pool at application startup and borrow a connection per transaction. Keep network calls to other systems outside open transactions. Use separate driver utilities for SQL identifiers and choose dynamic identifiers from a controlled list.

### SQLAlchemy 2.0 async sessions and Alembic

```python
from sqlalchemy import text
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine

engine = create_async_engine("postgresql+psycopg://user:password@localhost/app")
sessions = async_sessionmaker(engine, expire_on_commit=False)

async def count_facility(facility_id: int) -> int:
    async with sessions() as session:
        result = await session.execute(
            text("SELECT count(*) FROM inspections WHERE facility_id = :id"),
            {"id": facility_id},
        )
        return result.scalar_one()
```

The URL selects psycopg as the driver. Load the application's DSN from protected environment settings. The engine and factory can be shared while each independently executing task has its own session. The session holds transactional state and an identity map. **expire_on_commit=False** keeps already-loaded attributes available after commit. That helps avoid implicit database I/O from expired attribute access, while callers must know when to refresh values. The named parameter is bound separately. **scalar_one()** checks there is exactly one result row and returns its first value. With three facility inspections the result is the integer three. For related writes use the factory's transaction context. For ORM queries load relationships explicitly, because hidden I/O from deferred attribute access can fail under asyncio. Dispose the engine at shutdown.

Alembic compares model metadata and the current schema. **alembic revision --autogenerate -m "add inspection status"** proposes a revision where the message flag gives it a name. Review every rename, type, constraint, extension, and backfill. **alembic upgrade head** applies pending revisions to the latest target. Run both upgrade-from-previous and fresh-install tests. To introduce a required field on a busy table, add compatible nullable storage, deploy writes that populate it, backfill in bounded batches, validate, then enforce the required rule. Concurrent index builds need a migration context outside a standard transaction block and a cleanup plan after failed builds. Evaluate locks and I/O. Design for application versions overlapping during the change.

### Match vector operators to indexes

```sql
CREATE INDEX passages_embedding_cos ON passages USING hnsw (embedding vector_cosine_ops);
SELECT id, embedding <=> '[1,0,0]'::vector AS distance
FROM passages
ORDER BY embedding <=> '[1,0,0]'::vector
LIMIT 5;
```

The cosine operator returns distance, where smaller is closer. Direct ascending distance with a limit can use the matching operator class. Display similarity separately to avoid changing the indexed sort expression. L2 uses the **<->** operator and **vector_l2_ops**. A stored unit vector aligned with the query scores zero distance. Give null or zero vectors a documented rejection or fallback policy when using cosine.

Host port 55432 maps to PostgreSQL's container port 5432, and the environment options initialize the lab role and database. These credentials are for synthetic local data. The container runs in the background and is removed on stop. Save the following as **schema.sql**.

```sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE passages (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    depot text NOT NULL,
    body text NOT NULL,
    metadata jsonb NOT NULL DEFAULT '{}'::jsonb,
    embedding vector(3) NOT NULL,
    terms tsvector GENERATED ALWAYS AS (to_tsvector('english', body)) STORED
);
CREATE INDEX passage_depot ON passages (depot);
CREATE INDEX passage_terms ON passages USING gin (terms);
CREATE INDEX passage_embedding ON passages USING hnsw (embedding vector_cosine_ops);
INSERT INTO passages (depot, body, metadata, embedding) VALUES
    ('north', 'Inspect brake pads for uneven wear.', '{"revision": 3}', '[1,0,0]'),
    ('north', 'Inspect coolant level before startup.', '{"revision": 2}', '[0,1,0]'),
    ('south', 'Inspect brake reservoir pressure.', '{"revision": 1}', '[1,0,0]');
```

The generated term vector normalizes each stored passage with a stable search configuration. The JSONB fixture holds source revision metadata. A real design can link depot and document revision to parent records using foreign keys. Small fixtures can use sequential scans even when the indexes exist.

```python
# search.py
import asyncio
import os

import psycopg


async def main() -> None:
    async with await psycopg.AsyncConnection.connect(os.environ["DATABASE_URL"]) as conn:
        async with conn.cursor() as cur:
            await cur.execute(
                """
                WITH lexical AS (
                    SELECT id, row_number() OVER (ORDER BY score DESC, id) AS rank
                    FROM (
                        SELECT id, ts_rank(terms, q.query) AS score
                        FROM passages
                        CROSS JOIN websearch_to_tsquery('english', %s) AS q(query)
                        WHERE depot = %s AND terms @@ q.query
                        ORDER BY score DESC, id LIMIT 8
                    ) AS candidates
                ), semantic AS (
                    SELECT id, row_number() OVER (ORDER BY distance, id) AS rank
                    FROM (
                        SELECT id, embedding <=> %s::vector AS distance
                        FROM passages WHERE depot = %s
                        ORDER BY distance LIMIT 8
                    ) AS candidates
                ), combined AS (
                    SELECT id, 1.0 / (60 + rank) AS score FROM lexical
                    UNION ALL
                    SELECT id, 1.0 / (60 + rank) AS score FROM semantic
                )
                SELECT p.body, p.metadata ->> 'revision' AS revision
                FROM combined
                JOIN passages AS p USING (id)
                GROUP BY p.id
                ORDER BY sum(combined.score) DESC, p.id
                LIMIT 3
                """,
                ("brake pads", "north", "[1,0,0]", "north"),
            )
            for body, revision in await cur.fetchall():
                print(f"r{revision} {body}")


if __name__ == "__main__":
    asyncio.run(main())
```

The lexical branch parses natural search text and uses the matching operator to filter based on indexed terms. It sorts by rank and ID. The semantic branch uses a raw distance order that can fit a nearest-neighbor access path. Each branch obtains at most eight candidates and assigns ranks with a window function. The union keeps a contribution from each branch. Grouping by primary key combines those contributions and the JSONB extraction operator returns the revision as text. Both candidate branches bind the depot before fusion. In production, derive the scope from an authorized server context, then test with the application's actual role. Row-level security can add another boundary.

Install the driver with **python -m pip install "psycopg[binary]"**. The optional binary extra bundles its runtime dependencies for local setup. Run **docker exec -i atlas-rail-db psql -U lab -d rail_search -v ON_ERROR_STOP=1 < schema.sql**. The interactive input flag feeds the file to the client inside the container. The SQL variable setting stops execution on the first error. Run the schema against a fresh lab database. Run **python search.py**. Expected output starts with **r3 Inspect brake pads for uneven wear.** and follows with the north coolant passage. The south depot passage never appears.

Change the query text to coolant and the fixture vector to **[0,1,0]** and predict the reversed ranking. Change only the lexical text back and explain the mixed evidence. For a production evaluation, add curated paraphrases, exact codes, permission-filtered queries, and empty results. Compare approximate search against exact filtered neighbors and use retrieval failures to choose index settings. Plan an encoder upgrade by backfilling a second version, comparing both read paths in evaluation, and switching only after recall, latency, and source attribution checks pass. When finished, run **docker stop atlas-rail-db** to remove the disposable lab database.

## 5. Common Pitfalls & Debugging Playbook

### 1. Two requests claim the last unit

**Symptom:** Concurrent checkouts report success after both saw one unit in stock.

**Root Cause:** Validation and write were separate. An ordinary read can see the same stock across sessions before either update acquires a lock.

**Diagnostic:** Run the reservation concurrently in two independent sessions and compare returned rows and committed reservations against the starting state.

**Fix:** Express the predicate in the write and commit stock and reservation together. Use a constraint for structural uniqueness. Lock a shared coordinating row or use Serializable with bounded retries for a multi-row invariant.

### 2. Table size grows without more live data

**Symptom:** Query time and heap size rise while the number of live records stays steady.

**Root Cause:** Updates create row versions. A long-lived transaction can hold the visibility horizon back, and maintenance can have insufficient capacity.

**Diagnostic:** Examine transaction start times and idle-in-transaction sessions in the activity view. Compare estimated dead tuple counts and last autovacuum times in table statistics against write load.

**Fix:** End idle transactions, move external calls beyond transaction boundaries, and tune autovacuum for measured churn. Check storage capacity and maintenance progress before heavier operations.

### 3. The planner ignores a new index

**Symptom:** The plan shows a sequential scan or an explicit sort.

**Root Cause:** The filter may be broad, or index expressions, types, order, or operator class may differ from the query.

**Diagnostic:** Compare estimates with actual rows and buffers on representative data. Check the operator and ordering against the index definition.

**Fix:** Refresh stale statistics, align predicates with the available access path, and keep indexes whose measured read gains justify storage and write costs. A sequential scan can be the best plan for broad access.

### 4. Filtered search returns very few results

**Symptom:** A small tenant has enough eligible data yet receives fewer than the requested results.

**Root Cause:** Candidate generation and authorization can occur at different stages of the plan.

**Diagnostic:** Compare exact to approximate results under the same filter. Inspect removed rows, candidate settings, distance operators, and model versions.

**Fix:** Use exact ranking for a small eligible slice or increase search effort based on measurements. Check whether iterative scanning, partitioning, or a suitable partial index fits the access pattern.

### 5. An index migration stalls application writes

**Symptom:** Writes wait for a long time after a schema change begins.

**Root Cause:** DDL needs locks, and earlier open transactions may block the migration even before work starts.

**Diagnostic:** Inspect wait events and blocking session IDs using the activity view and the **pg_blocking_pids** function. Replay the migration on a copy with representative transactions.

**Fix:** Use staged compatible changes, lock wait limits, and concurrent index creation where applicable. Inspect interrupted results and plan repair before rerunning.

### Q1. Two transactions check the same inventory and then both reserve the last item. What should the design add?

- A. A longer HTTP timeout
- B. A database constraint or appropriate transaction-level concurrency control
- C. A JSONB field for the item label

<details>
<summary>Answer & Explanation</summary>

**Answer: B.** Put the invariant where concurrent writes can be coordinated. Test with competing transactions.

</details>

### Q2. HNSW retrieval under a selective tenant filter returns fewer rows than expected. What should you inspect?

- A. Client serialization only
- B. The operating system clock
- C. The plan, candidate set, and filtering order

<details>
<summary>Answer & Explanation</summary>

**Answer: C.** Approximate candidates can be filtered after the index scan. Compare with exact search and measure recall.

</details>

### Q3. Two sessions each deactivate a different backup responder after reading the same coverage snapshot. What remains possible at Repeatable Read?

- A. Write skew across two different rows
- B. Dirty reads from an uncommitted third session
- C. Changes to an existing committed value between ordinary reads in the same snapshot

<details>
<summary>Answer & Explanation</summary>

**Answer: A.** Each session writes a different row, so both transactions may commit. Coordinate on a shared coverage record or use Serializable with full-transaction retries.

</details>

### Q4. A GIN index uses a JSONB containment operator class. Which query shape fits?

- A. Sort by creation time
- B. Find rows containing a given metadata object
- C. Join every writer account to its display name

<details>
<summary>Answer & Explanation</summary>

**Answer: B.** The operator class can find matching JSONB components. Sorting needs an ordered path such as a B-tree. Joins depend on their predicates and estimates.

</details>

### Q5. EXPLAIN ANALYZE reports twelve actual rows and five hundred loops for an inner scan. How many rows did it emit approximately?

- A. 12
- B. 500
- C. 6,000

<details>
<summary>Answer & Explanation</summary>

**Answer: C.** The visible row figure is a per-loop average. Account for the repetition and inspect buffers to understand total work.

### Q6. Why should concurrently executing operations use distinct SQLAlchemy async sessions?

<details>
<summary>Answer & Explanation</summary>

An async session carries transactional state and an identity map. Interleaved tasks can conflict over the active connection and assumptions about pending writes or rollback. Share the factory and engine, then give each independent operation its own session.

</details>

### Q7. You need to replace a vector encoder while production search traffic continues. Design the release and identify what you would measure.

<details>
<summary>Answer & Explanation</summary>

Record the model, dimensions, normalization, and distance metric. Keep separate versioned vectors and indexes. Backfill and reconcile new writes, then compare authorized retrieval, labeled recall, latency, and source revision consistency before switching reads. Retain a usable prior read path during stabilization.

</details>

### Q8. Alembic proposes dropping a field and adding a similarly typed field. Both names refer to the same business fact. What should you check?
