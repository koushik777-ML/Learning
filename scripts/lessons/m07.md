## 1. The Mental Model

A container makes a process portable by packaging its userspace filesystem and declaring how it should run. The image answers “what files and defaults ship?” and the runtime answers “which privileges, resources, storage, and network paths does this particular instance receive?” Separating those questions lets one built artifact run in multiple environments with different policies.

Imagine a print shop receiving a sealed equipment kit and a separate room assignment. The kit contains the machine and compatible consumables. The room supplies power, storage, a door, and rules about who can enter. Changing the room should rarely require rebuilding the equipment kit. Similarly, a service's endpoint or credential should be runtime configuration, while its interpreter and Python dependencies belong in the image.

| Concept | What the contract controls | What to verify |
| --- | --- | --- |
| Image | Ordered filesystem layers, architecture, default command and environment | Can a separate machine pull and run the same digest? |
| Container | One runtime instance, its process tree and writable layer | Does it handle shutdown, resource limits, and restart correctly? |
| Mount | Filesystem location delegated to the runtime | Will the data survive removal or migration? |
| Network | Which addresses can reach a listening port | Can only the intended caller reach it? |
| Registry | Distribution by repository, tag, and digest | Can CI pin or roll back to the exact artifact? |

Containers share the host's kernel. A running process sees a Linux kernel with its own visible process IDs, mounts, and interfaces as configured. A macOS or Windows Docker Desktop machine usually boots a Linux VM for Linux containers. If you build on ARM and deploy on x86, a compatible userspace artifact is still required. An image manifest list can point a client to distinct OS/architecture-specific images. Copying an x86-only wheel into an ARM image will not make it portable.

A rebuild and a restart answer different questions. A restart tests the current image and runtime settings. A clean rebuild tests declared build inputs, including dependency versions and base images. For production reliability, build once, record the artifact digest, exercise the release on a known platform, and redeploy that digest with environment-specific settings. A tag like `latest` can move and says nothing about release order.

## 2. Core Architecture & How It Works Under the Hood

```text
 source + lockfile + Dockerfile
             |
      build context -> BuildKit -> OCI layers + image config -> registry
                                   |
                           runtime selects image
                                   v
       +-------- Linux host kernel / container platform -------+
       | cgroups: CPU, memory, PIDs                            |
       | namespaces: PID, mount, network, UTS, IPC, user*       |
       |                                                      |
       | container writable layer -> overlay -> image layers  |
       | /data -> delegated named volume                      |
       | eth0 -> virtual pair -> bridge -> companion service  |
       +------------------------------------------------------+
                      * when user namespace isolation is configured
```

### Process identity and kernel controls

The Docker client sends a request to a daemon. Through its container runtime, the daemon prepares the root filesystem and runtime settings and asks the kernel to start the process. Namespaces change the process's view of names and resources. A PID namespace can make your web server PID 1, and a network namespace can give it an independent loopback interface. Cgroups account for resources used by the process tree and enforce configured ceilings. A memory limit does not alter a Python object model. It controls how much memory the cgroup as a whole can use before reclaim and possible OOM termination. Kernel scheduling can throttle a service at its CPU quota even if its processes are running.

PID 1 has lifecycle responsibilities. Docker sends its stop signal to PID 1, waits for the stop timeout, then can terminate remaining processes. Shell-form startup can interpose a shell that does not forward termination. Exec-form startup makes your server the direct recipient. A Python server should stop accepting work, drain or cancel work within a budget, and close clients. If the application launches child processes and lacks reaping logic, a minimal init can reap orphaned children and help forward signals. A restart policy reacts to process failures. Healthy operation still requires the application to honor the runtime contract.

### Layers, cache keys, and writable state

An image manifest names an image configuration and content-addressed compressed layers. The runtime mounts a merged view of read-only image content and a container-specific writable layer. A write to a lower-layer file can copy it into the writable layer before modifying it. Deleting a lower-layer file in a later image layer hides it from the merged view. The original bytes still exist in the earlier layer. This matters for both image size and credential hygiene. Deleting a credential after using it in an earlier build step does not remove it from distributed layers.

BuildKit reuses results when the relevant inputs and prior build state match a cached operation. A `COPY . .` before dependencies couples dependency installation to edits in every copied file. Copy just the manifest and lockfile first, install dependencies, and add application code afterward. Exclude local environments, credentials, and large datasets through `.dockerignore`. Build-time cache mounts speed package downloads and need no place in the final image. They do not guarantee reproducibility. Exact versions, hashes, a pinned base image digest, and tested platform-specific artifacts serve that purpose.

Storage ownership follows the selected mechanism. An ordinary container write is tied to the container instance. A named volume lives outside that instance on the Docker host and can be attached to a replacement. A bind mount maps an explicit host path and depends on the host's tree and permissions. Container replacement on a different host will need data migration, shared storage, or an external service. Mounting onto an existing image directory hides the original view there. Docker can populate a fresh named volume from the image directory initially, whereas a bind mount shows the existing host path. Make initialization deliberate and idempotent.

### Port publishing and service discovery

Each container's loopback refers to that container. An API can reach a companion on a user-defined bridge by resolving the companion's service name. The host reaches a published port if the application listens on a container interface accessible through the bridge and the chosen host port is available. Specifying `EXPOSE` documents the internal port. Publishing it is a separate runtime operation. Publishing `127.0.0.1:8080:8000` maps host loopback port 8080 to container port 8000 and limits host-side reach compared with a wildcard publish. Companion services on the same bridge can reach each other without publishing. Design and test inbound reachability and outbound dependency access separately.

### Image and runtime trust

A container's root user has more privileges than a dedicated application identity. A non-root user, a read-only root filesystem, a limited writable mount, dropped capabilities, and a no-new-privileges policy reduce accidental and malicious side effects. Ensure the app still can read assets, write only its intended directories, and bind its service port. Rootless Docker also changes how the daemon runs. It addresses a different boundary from `USER` in a Dockerfile. Keep the Docker socket out of app containers because control of the daemon can grant broad control over the host. Treat container isolation, dependency provenance, and network access policy as independent controls.

## 3. Complete Command, Query & Python Syntax Reference

### Build and run one artifact

```bash
docker build --tag pantry-api:dev .
docker run --rm --name pantry-dev --publish 127.0.0.1:8080:8000 pantry-api:dev
docker logs --tail 30 pantry-dev
docker stats --no-stream pantry-dev
```

`docker build` uses the current directory as the build context. The tag names this local build for convenience. In `docker run`, `--rm` removes the container after exit, `--name` gives a stable lookup name, and `--publish` maps address and ports as described above. Run the log and stats commands in a second terminal while the server is running. `--tail 30` limits displayed log lines, and `--no-stream` returns a snapshot of CPU, memory, and other resource usage. The example image is created in the lab. Its `/live` endpoint should answer on host port 8080. Individual container labels and stats vary by host.

### Isolate filesystem choices

Use a read-only bind mount when replaying a curated local input directory and a named volume when a replacement on the same host must reuse app-managed data. `--mount type=bind,src=/absolute/fixtures,dst=/input,readonly` requires an existing host directory and prevents writes through the mount. `--mount type=volume,src=pantry-data,dst=/data` gives the container a named volume. Paths and usernames are interpreted where the daemon runs, which matters when the client controls a remote Docker context. Avoid mounting a developer's whole home directory to “make files available.” Mount the smallest specific location and document who owns it.

If a slim image needs a system library for a Python wheel, compile or download wheels in the first stage and install required runtime libraries in the final stage. A compatible virtual environment can also be copied between stages that share interpreter path and base ABI. Prefer slim bases when you need ordinary utilities and runtime libraries. Distroless bases omit much of the interactive userspace. They can simplify the runtime package inventory but require planning for compatible libraries and approved diagnostic tooling. The smallest image is rarely the main goal if it cannot be understood and maintained.

### Runtime limits and deployment boundaries

Typical runtime flags include `--memory 512m`, `--cpus 1.0`, and `--pids-limit 128`. These set the container memory limit, CPU quota relative to one CPU, and process/thread count limit. Use measured load and process behavior to choose values. Test under those values, including startup and graceful stop. Log stdout/stderr and let the runtime or logging driver collect it. Make Python logs flush promptly with `PYTHONUNBUFFERED=1`, and avoid output that contains sensitive inputs or credentials.

Use direct array form for the command, for example `CMD ["python", "-m", "uvicorn", "app:app", "--host", "0.0.0.0"]`. Python's `-m` resolves an installed module in its environment. `app:app` tells Uvicorn to import the `app` object from the `app` module. `--host` defines the address in the container's network namespace. Regular application credentials belong in the deployment's secret mechanism. Registry or dependency credentials needed by builds belong in temporary secret mounts rather than build arguments or copied files. Pin base images by digest and track updates through a controlled rebuild process. An immutable old image remains old even if a fixed base tag now exists.

## 4. End-to-End Real-World Reference Example

A food pantry records the total kilograms received each day. The local lab uses a Python HTTP service and a Redis-backed counter. The API is replaceable. The counter persists separately and exposes a good test of startup, connectivity, and volume ownership. Production intake would also need authorization, date partitioning, and idempotency to avoid double-counting ambiguous requests. This bounded local demo focuses on the container contract.

```text
pantry-intake/
  app.py
  requirements.txt
  Dockerfile
  compose.yaml
  .dockerignore
```

**`app.py`**

```python
import os

from fastapi import FastAPI, HTTPException, Query
from redis import Redis
from redis.exceptions import RedisError

app = FastAPI()
redis = Redis.from_url(
    os.getenv("REDIS_URL", "redis://store:6379/0"),
    socket_connect_timeout=0.5,
    socket_timeout=0.5,
)

@app.get("/live")
def live():
    return {"status": "alive"}

@app.get("/ready")
def ready():
    try:
        redis.ping()
    except RedisError as exc:
        raise HTTPException(503, "Storage is unavailable") from exc
    return {"status": "ready"}

@app.post("/intake")
def receive(kg: int = Query(ge=1, le=100)):
    try:
        return {"total_kg": redis.incrby("pantry:test:intake", kg)}
    except RedisError as exc:
        # An interrupted response can mean a completed write. Reconcile first.
        raise HTTPException(503, "Intake result is unavailable") from exc
```

`Redis.from_url` configures a connection pool in the Python process. The URL names the companion service, its internal port, and database zero. Socket connection and read timeouts bound dependency waits. Synchronous FastAPI routes allow this blocking client to run in the framework's thread pool rather than blocking the event loop directly. `Query` constrains kilograms to an integer from 1 through 100. Redis performs the increment atomically across simultaneous requests. Liveness reports whether the process can handle a request. Readiness checks whether it can currently reach the dependency needed for useful work.

**`requirements.txt`**

```text
fastapi==0.115.12
uvicorn==0.34.2
redis==5.2.1
```

**`Dockerfile`**

```dockerfile
FROM python:3.12-slim AS build
WORKDIR /build
COPY requirements.txt .
RUN python -m venv /opt/venv && /opt/venv/bin/pip install --no-cache-dir -r requirements.txt

FROM python:3.12-slim
ENV PATH="/opt/venv/bin:$PATH" PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1
WORKDIR /app
COPY --from=build /opt/venv /opt/venv
COPY --chmod=0444 app.py .
USER 10001:10001
EXPOSE 8000
CMD ["python", "-m", "uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]
```

The first `FROM` names a build stage. `WORKDIR` uses an absolute build path, and `COPY requirements.txt .` makes the dependency cache key independent of app source edits. `pip -r` installs the file's requirements and `--no-cache-dir` omits download caches in the environment build. The second stage receives only the virtual environment and source. The source copy is explicitly readable by the runtime identity even if the checkout uses a restrictive file mode. Both bases use the same Python minor version and interpreter path. `PATH` selects the venv, immediate logging helps diagnosis, and disabling bytecode writes simplifies a read-only filesystem. `USER` uses a numeric unprivileged UID and GID. `EXPOSE` records the server's port, while `--port` selects the actual listener. For a controlled build, use a full locked dependency set and pinned image digest alongside this stage structure.

**`compose.yaml`**

```yaml
services:
  store:
    image: redis:7.4-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - intake-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 2s
      timeout: 1s
      retries: 8
  api:
    build: .
    environment:
      REDIS_URL: redis://store:6379/0
    depends_on:
      store:
        condition: service_healthy
    ports:
      - "127.0.0.1:8080:8000"
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/ready', timeout=1)"]
      interval: 2s
      timeout: 2s
      retries: 10
    read_only: true
    tmpfs: ["/tmp"]
    cap_drop: ["ALL"]
volumes:
  intake-data:
```

Compose creates a project network and gives the `store` service a DNS name. Redis uses an append-only log in `/data`. The volume is named at the top level and mounted only into Redis. The health test runs Redis's client within the `store` container. Intervals, timeout and retries control the health state, and the API's dependency condition gates initial startup until Redis is healthy. The API's own health test makes an HTTP request within its container so Compose can also wait until the Python server is ready. A later outage still needs application handling. Host loopback exposes just the API. The API's root filesystem is read-only except for the temporary memory-backed mount. Dropping capabilities limits kernel privileges. The lab Redis is reachable by companions on its project network. Production database credentials, backups, replication, and restricted network reachability need explicit design.

**`.dockerignore`**

```text
.git
.env
.venv
__pycache__
```

Start in `pantry-intake` and run these commands against a Docker engine with Compose v2.

```bash
docker compose up --build -d --wait
curl -fsS http://127.0.0.1:8080/ready
curl -fsS -X POST 'http://127.0.0.1:8080/intake?kg=7'
docker compose down
docker compose up -d --wait
curl -fsS -X POST 'http://127.0.0.1:8080/intake?kg=2'
docker compose down
```

`up` converges the declared services, `--build` builds the app image, `-d` detaches, and `--wait` waits for declared health or running state. `curl -f` fails on an HTTP error, `-sS` hides progress while still printing failures, and `-X POST` selects the mutating HTTP method. On a fresh volume the responses are `{"status":"ready"}`, `{"total_kg":7}`, and then `{"total_kg":9}`. `down` removes the service containers and project network and retains declared named volumes by default. A running service can still provide a bad response, so treat the HTTP calls as the functional checks. Try stopping `store` in your lab and verifying that liveness succeeds while readiness fails. Restart it and verify recovery. Confirm the API runs under UID 10001 by inspecting the process identity inside the container.

## 5. Common Pitfalls & Debugging Playbook

### Container up, browser refused

**Symptom:** Docker reports a running process, but a host call cannot connect.
**Root Cause:** The application is bound to its own loopback, or a different host port was published. A container's port and the host port are separate values.
**Diagnostic:** Run `docker port pantry-dev` to inspect the mappings. Check `docker logs --tail 30 pantry-dev` for the address and port the process bound. Compare them to the host URL.
**Fix:** Bind the app to an interface available in its network namespace, publish the intended host address and port, and probe the actual endpoint. Preserve loopback-only host visibility for local exercises.

### Dependencies reinstall after every source edit

**Symptom:** Each code fix spends most of the build reinstalling Python packages.
**Root Cause:** Source code is copied before the install or the context includes changing files unrelated to dependency resolution.
**Diagnostic:** Run the build twice, changing only app source between runs, and compare which build steps report cached results.
**Fix:** Copy dependency artifacts first, install in an independent stage, and exclude unrelated files with `.dockerignore`. Keep cache speed and dependency pinning as separate requirements.

### Replacement loses data or sees an empty directory

**Symptom:** A container replacement resets state or cannot see seed files expected under a path.
**Root Cause:** State was written only to the writable overlay or a mount now covers image content under the destination path.
**Diagnostic:** Use `docker inspect pantry-dev` and inspect its `Mounts` entries for type, source, destination, and writable flag. Check which path the application actually writes.
**Fix:** Put state in a deliberately initialized volume or external datastore. Supply seed data at a different path, and test persistence by removing and recreating the service in a disposable environment.

### Worked on a developer laptop, crashes in constrained runtime

**Symptom:** The API restarts under load or hangs during deployment.
**Root Cause:** A resource ceiling, ABI mismatch, filesystem assumption, or missing termination behavior has been masked by the local machine.
**Diagnostic:** Inspect `State.ExitCode` and `State.OOMKilled` through `docker inspect`. A killed process and an OOM termination are not interchangeable. Compare architecture and libc of the installed wheel, application startup stderr, and release runtime limits.
**Fix:** Test the target architecture and production limits in CI. Choose compatible wheels, put temporary writes in the designated location, and implement shutdown with a deadline.

### Permission failed after switching away from root

**Symptom:** The same image starts as root and fails under its intended application UID.
**Root Cause:** A mounted directory has host ownership the application identity cannot write, or a dependency expects a home directory or privileged port.
**Diagnostic:** Inspect UID and GID, mount type, path ownership and mode, then locate the failing system operation in application logs.
**Fix:** Grant the dedicated ID access only to the required mount, set an explicit writable temporary directory if needed, and use an unprivileged listener port.

## 6. 3 Standalone Practice Projects

### Project 1: Print Layout Worker Image

**Domain:** Commercial printing

A printer prepares page layouts from customer-supplied design files. Use curated fixtures rather than sensitive artwork and keep the layout output deterministic. Define what belongs in build tooling, what the runtime needs, and what should be a mounted input. Evaluate the same input on a clean machine so the final image demonstrates independence from a developer's workstation.

#### Recommended Folder Structure

Use a print-worker directory with app/layout.py, Dockerfile, pyproject.toml, a dependency lock, fixtures/sample-layout.txt, tests/test_layout.py, and docs/build-notes.md.

#### Build Milestones

1. Separate build and runtime dependencies and arrange layers for predictable cache reuse.
2. Compare build times and confirm the runtime runs as a non-root user.

#### Acceptance Checklist

Changing only application source preserves dependency stages. Changing a pinned dependency reruns the relevant install. A freshly started worker handles a read-only sample and writes identical output to a controlled writable directory. Startup logs identify the version without exposing input material.

### Project 2: Field Sensor Replay Environment

**Domain:** Environmental monitoring

An environmental team replays sensor records to regenerate daily water-quality summaries. Inputs are versioned snapshots. Outputs may outlive a worker, and two independent runs must not mix datasets. Specify network reachability, write authority, and what happens when the input is corrupt or the disk fills.

#### Recommended Folder Structure

Use sensor-replay with replay/reader.py, replay/aggregate.py, compose.yaml, fixtures/site-a.txt, tests/test_replay.py, and docs/retention.md.

#### Build Milestones

1. Design network boundaries and choose bind mounts for input and volumes for retained outputs.
2. Remove and recreate the container and verify the documented output lifecycle.

#### Acceptance Checklist

A clean worker can replay one sample and rejects malformed records predictably. The worker cannot change its read-only input. Worker replacement keeps the expected summaries, and reprocessing the same sample produces stable results without silently duplicating them.

### Project 3: Library Digitization Stack

**Domain:** Archives

An archive uploads sample scans for processing and later checks their status. Keep authoritative work state outside transient API files, design what happens when a worker receives the same job twice, and assign ownership for shutdown and retained data. Publish only the interface required by a caller.

#### Recommended Folder Structure

Use library-digitization with api/main.py, worker/scan.py, Dockerfile, compose.yaml, fixtures/sample-pages.txt, tests/test_lifecycle.py, and docs/recovery.md.

#### Build Milestones

1. Define service dependencies, health checks, persistent data, and resource limits.
2. Simulate a slow dependency and verify bounded startup and clean recovery.

#### Acceptance Checklist

The API queues usable work only when its required storage is reachable. Interrupting one job and replacing the worker leaves a clear resumable or failed state. Published ports expose only the API and logs identify the failing component during a slow dependency.

## 7. Mastery Checkpoint Questions

### Q1. Installing dependencies reruns every time application source changes. What usually improves layer reuse?

- A. Copy dependency manifests and install before copying application sources
- B. Run every build without the cache
- C. Store artifacts only in a runtime volume

<details>
<summary>Answer & Explanation</summary>

**Answer: A.** Layers are invalidated by changed inputs and preceding layers. Put slower, less frequently changing work first.

</details>

### Q2. A container is removed and its output was written only to its writable layer. What should retain it across replacements?

- A. A new image label
- B. A persistent volume or supported external storage
- C. A larger memory limit

<details>
<summary>Answer & Explanation</summary>

**Answer: B.** The writable container layer has the container's lifecycle. Use an explicitly persistent storage mechanism.

</details>

### Q3. The host cannot reach a published port even though the process responds to its own internal localhost. What should you check first?

- A. Whether the app listens on an interface reachable from the container network
- B. Whether the registry tag is lowercase
- C. Whether the image uses a named volume

<details>
<summary>Answer & Explanation</summary>

**Answer: A.** A loopback listener inside a container is local to its network namespace. The host port mapping needs to reach a listener on the appropriate container interface.

</details>

### Q4. An image was built with a credential copied into one layer and removed in the next. What should happen?

- A. Keep the image because the file is not in its final filesystem
- B. Rotate the credential and rebuild using a temporary secret mount
- C. Keep only the image manifest

<details>
<summary>Answer & Explanation</summary>

**Answer: B.** Earlier layers retain their original bytes and are distributed as part of the image. Remove the compromised artifact from use and pass credentials through the builder's temporary secret mechanism.

</details>

### Q5. A Python service runs a native dependency on ARM locally and fails to start on an x86 deployment target. What should you verify?

- A. Whether the container IP changed
- B. Whether volume copy-up ran after startup
- C. The target manifest and architecture and ABI of installed wheels

<details>
<summary>Answer & Explanation</summary>

**Answer: C.** Container packaging does not remove platform or libc constraints. Test the selected base and native dependencies on the deployed architecture.

</details>

### Q6. How would you prove that restarting the pantry API is independent of losing its authoritative counter?

<details>
<summary>Answer & Explanation</summary>

Record a nonzero total through the HTTP API. Replace the API container and confirm the same state remains through Redis. Then replace the Redis container with its original named volume and verify the total again. Check both the volume mapping and the app result. Test backup and restoration separately if the system must survive host loss.

</details>

### Q7. Explain the difference between CPU, memory, and permission symptoms when hardening a media worker.

<details>
<summary>Answer & Explanation</summary>

A CPU quota can throttle the worker and increase latency. Memory exhaustion can lead to termination and an OOM state. Path access errors involve ownership, capabilities, mount access, or an explicit read-only filesystem. Compare measured resources with the exit state and error context before changing the relevant bound, write path, or identity.

</details>

Confirm the selected image digest, runtime command, listener and publisher, expected mounts, and observed cgroup limits. For each requirement, prove the behavior through the application's actual interface. A smaller image, a running process, and a successful build each answer different questions.
