## 1. The Mental Model

Structured function calling expresses the model's choice as data that the application can check and dispatch. Multi-agent protocols take the same need for explicit contracts across a service boundary. An argument schema solves shape ambiguity, while an authenticated task interface solves delegation, lifecycle, and response correlation. The two belong at different boundaries.

Picture a facilities desk issuing a maintenance ticket. A well-formed ticket names a supported operation and contains the required fields. The desk still checks who requested it and whether that building is in scope. When the ticket is forwarded to another team, the receiving team issues its own task ID, reports progress, and delivers a work product. Each hop makes a local decision about authority.

| Boundary | Object that crosses it | Validation owed by the receiver |
| --- | --- | --- |
| Model to local host | Tool name and arguments | Schema, allowed tool, authorized resource, business invariants |
| Host to remote agent | Authenticated message carrying a task request | Caller identity, task scope, quotas, input shape, supported protocol |
| Remote agent to host | Message, task state, or artifact | Request correlation, lifecycle order, evidence provenance, artifact checks |
| Host to requester | Final answer and evidence | Applicability, uncertainty, citations, disclosure policy |

A typed function call is generally attractive when a host owns the tool and can make one bounded request. Remote delegation is useful when work has its own owner, scope, dependency graph, or long lifetime. A team that only needs a few query functions can keep them local. Each additional remote agent brings network failures, API versions, duplicate work, tracking, and review costs.

### Hermes-style tool calling and constrained decoding

A tool-capable model is trained to represent a function name and arguments in a particular serialization. Hermes-style models commonly support a chat template with tool definitions followed by a marked function-call block. The template belongs to the selected model and serving stack. Provider SDKs often normalize that block to a structured tool-call field. Check the supported signaling and schema conventions of the chosen model and inference runtime before mixing components.

During unconstrained generation, a model can emit prose where the caller expects JSON, omit a closing brace, or invent keys. During grammar-constrained generation, the runtime tracks parse state and masks tokens that cannot continue the permitted language. The model still chooses among candidates, producing a well-shaped result where the implementation supports the required rules. Server capabilities vary across JSON Schema keywords and combinations. Test the compatibility of required fields, enumerated options, nesting, and unions with the deployed decoder.

Distinguish four checks:

1. **Serialization:** Can the output be parsed within size and depth limits? Detect duplicates where the decoder would otherwise silently use the last occurrence.
2. **Structural contract:** Does the selected function exist and do the values match the schema? For closed objects, deny unknown fields. Reject implicit type coercion when ambiguity matters.
3. **Semantic and authority checks:** Is the operation legitimate for this actor and task? Check domain invariants, target resource scope, current versions, and review requirements.
4. **Execution result:** Did the operation complete, fail, or return an uncertain outcome? Check the result before passing it to the model or another service.

A constrained response may be a final typed answer or a tool-call proposal. Track them as different message types. An output saying “completed” is a claim. A verified tool result containing an operation ID and receipt provides stronger evidence that the action occurred.

### Orchestration topologies

| Topology | How work is coordinated | Works well when | Costs and safeguards |
| --- | --- | --- | --- |
| Supervisor-worker | One coordinator selects specialists and collects outputs | One team owns prioritization, task budgets, and final decisions | Supervisor can bottleneck. Bound fan-out and record its decisions |
| Hierarchical | Sub-coordinators own narrower work streams | Delegation reflects existing independent ownership domains | Depth compounds cost and obscures responsibility. Propagate deadlines, scopes, and trace context |
| Handoffs or swarm | A current worker transfers control to a specialist | Routing needs local domain knowledge and transitions are bounded | Handoffs can cycle. Track visited transitions, keep a fixed hop budget, and retain a clear final decision owner |

Parallel specialists help only when their work decomposes cleanly. Give every branch a purpose, a shared task context, a separate deadline, and an expected artifact shape. Define how the supervisor handles incomplete branches, for example accept two independent confirmations, wait for a particular required skill, or return “needs review.” Keep the merge deterministic where domain rules are explicit. Compare trusted source IDs, dates, and permitted categories before using another model to interpret disagreements.

### Agent-to-Agent discovery and lifetime

In A2A, one independently implemented agent client can talk to another agent service using shared protocol concepts. Pin compatible protocol versions and negotiate a supported binding. Concrete transports, field casing, and operation names depend on the version and binding, so use a conforming sample or SDK for the integration. Remote and local agents can use different orchestration frameworks and programming languages. The contract is the wire interface plus agreed semantics and artifact formats.

- An **Agent Card** advertises identity, interface URLs or bindings, supported skills, capabilities such as streaming, compatible input/output modes, and security requirements. Discovery may use the version's well-known location or a configured registry. Resolve the peer through a trusted configuration or registry and apply identity and endpoint verification. The advertised card alone does not grant access.
- A **message** carries an ID, sender role, and parts such as text, structured data, or referenced files. A turn can produce a direct reply, or a remote service can create a **task** for work that needs tracking. Separate a conversation or context ID from an individual task ID. A context groups related turns, while a task has one lifecycle.
- **Task state** represents progress, for example submitted, working, input required, completed, failed, or canceled. Use the negotiated version's exact states and legal transitions. A network timeout means the client did not observe an answer. It does not tell you whether work started or completed.
- An **artifact** is an output such as a result record, file, or report. The receiver still validates type, size, version, and provenance. Treat URLs and attachments as restricted inputs, and keep artifact access scoped to authenticated task owners.
- Polling is straightforward for long waits. Use a bounded interval with jitter and a total deadline. When streaming is supported, consume available status and artifact events, and reconcile with an authoritative task read after disconnect. A stream can fail even as its task keeps running.
- Cancellation requests an orderly stop. Observe the next confirmed terminal state and the retained effect record. A task might complete just before cancellation arrives. Scope cancellation to the owner or a separately authorized operator.

Use a client-side logical submission ID and reconcile it with the remote task ID. A repeated HTTP POST may create duplicate tasks unless the peer documents an idempotency contract. Model output requesting delegation does not authorize arbitrary endpoint selection. Select the peer from an application-controlled registry. In cross-organization use, pass a minimum-scope identity and only the context needed for the job.

### Contrast with Model Context Protocol

MCP exposes capabilities such as tools, resources, and prompts for a host to use. A2A is intended for delegation to a peer with an independent task lifecycle. A remote agent can use local integrations while fulfilling a delegated request. A caller only needs the peer's stated skill and artifact contract. It can avoid pulling the peer's internal tools or chain of decisions into its own model context.

## 3. Complete Command, Query & Python Syntax Reference

### Build a closed argument schema

The schema below describes one tool's arguments. The same schema can be checked in a test against the model runtime's decoder support. Provider tool wrappers differ, so the argument object is separate from the SDK-specific function declaration.

~~~json
{
  "type": "object",
  "properties": {
    "region": { "type": "string", "enum": ["north", "south"] },
    "limit": { "type": "integer", "minimum": 1, "maximum": 5 }
  },
  "required": ["region", "limit"],
  "additionalProperties": false
}
~~~

`type` chooses a JSON object at the outer level. `properties` describes each key. `required` makes those keys mandatory; declaring a property alone leaves it optional. `enum` enumerates supported region names. `minimum` and `maximum` are inclusive integer bounds. `additionalProperties` closes the object, helping catch misspelled and invented arguments. A region allowed by the schema can still be outside the caller's scope.

### Keep names, arguments, results, and errors distinct

A robust host constructs a registry of known functions and their validators at startup. A tool name is a key into that registry. Pass a typed argument object and trusted request context to the chosen callable. The callable returns a structured result with a status and the allowed data. For a retriable service error, carry a stable operation identity and a bounded deadline. Validation or authorization errors generally stop or redirect a workflow. A valid correction changes the proposed arguments and should be recorded.

When a tool returns an external record, inspect it before showing it to a model. For example an inventory reply can contain a product identifier and count, while irrelevant supplier notes remain outside the prompt. Associate the tool result with its call ID so callers can distinguish parallel outputs and retain evidence paths.

### Model remote results explicitly

For a remote agent, design an interface around a verified peer, submission, status, cancellation, and validated artifacts. Track `client_request_id`, `peer_id`, `remote_task_id`, `last_seen_status`, `deadline`, and the caller identity or a reference to it. Use a durable lookup table keyed by the peer and remote task ID because IDs from different services may collide. Keep trace IDs for diagnostics and audit-friendly operation IDs for joining records. Avoid claims that a trace ID is an authentication credential or idempotency key.

A status adapter maps known protocol states to internal ones and records the source state. Fail on unknown or malformed states rather than treating them as successful. With an “input required” state, identify who can provide more input and when the request will expire. Follow terminal states such as completed, failed, and canceled with an artifact check appropriate to the domain.

## 4. End-to-End Real-World Reference Example

### Ferry terminal availability review

An operations dashboard asks a specialist to review a short list of departure windows. This local Python lab runs strict argument checks, enforces region restrictions from caller context, and delegates to a simulated specialist. The duplicate request returns the same task ID, and the artifact appears only once the task reaches a terminal state. The simulation demonstrates lifecycle behavior while avoiding deployed services and model credentials.

~~~text
ferry-review/
  ferry_lab.py    proposal validation, scoped request, simulated task lifecycle
~~~

Create `ferry_lab.py` with the following content.

~~~python
import json

def unique_object(pairs):
    result = {}
    for key, value in pairs:
        if key in result:
            raise ValueError(f"Duplicate key: {key}")
        result[key] = value
    return result

def decode_proposal(raw: str, allowed_region: str) -> tuple[str, int]:
    if len(raw.encode("utf-8")) > 500:
        raise ValueError("Proposal too large")
    data = json.loads(raw, object_pairs_hook=unique_object)
    if not isinstance(data, dict) or set(data) != {"region", "limit"}:
        raise ValueError("Unexpected arguments")
    region, limit = data["region"], data["limit"]
    # bool subclasses int in Python, so check the exact type.
    if not isinstance(region, str) or region not in {"north", "south"}:
        raise ValueError("Unknown region")
    if type(limit) is not int or not 1 <= limit <= 5:
        raise ValueError("Invalid limit")
    if region != allowed_region:
        raise PermissionError("Region outside caller scope")
    return region, limit

class LocalSpecialist:
    def __init__(self) -> None:
        self.tasks: dict[str, dict] = {}

    def submit(self, request_id: str, region: str, limit: int) -> str:
        prior = self.tasks.get(request_id)
        if prior:
            if prior["arguments"] != (region, limit):
                raise ValueError("Request ID already has different arguments")
            return prior["id"]
        task_id = f"review-{len(self.tasks) + 1}"
        self.tasks[request_id] = {
            "id": task_id,
            "arguments": (region, limit),
            "state": "working",
        }
        return task_id

    def finish(self, request_id: str) -> None:
        task = self.tasks[request_id]
        if task["state"] == "working":
            region, limit = task["arguments"]
            windows = ["08:30", "09:15", "10:00"]
            task["artifact"] = {"region": region, "windows": windows[:limit]}
            task["state"] = "completed"

allowed_region = "north"  # In a real service this comes from authenticated policy.
region, limit = decode_proposal('{"region": "north", "limit": 2}', allowed_region)
specialist = LocalSpecialist()
first = specialist.submit("request-72", region, limit)
print(first, specialist.tasks["request-72"]["state"])
assert specialist.submit("request-72", region, limit) == first
specialist.finish("request-72")
print(specialist.tasks["request-72"]["artifact"])

try:
    decode_proposal('{"region": "south", "limit": 2}', allowed_region)
except PermissionError as error:
    print(error)
~~~

Run `python ferry_lab.py` from the project directory. This uses the local interpreter and reads the named script. The expected output is:

~~~text
review-1 working
{'region': 'north', 'windows': ['08:30', '09:15']}
Region outside caller scope
~~~

`object_pairs_hook` decodes each JSON object from ordered pairs. This preserves visibility into duplicates before a dictionary could overwrite entries. `type(limit) is int` denies booleans because Python defines `bool` as a subclass of `int`. In `submit`, the same ID returns the same task only when the arguments match. `finish` observes the state before publishing the synthetic artifact.

For a real integration, keep the validated proposal and caller scope separate. Bind idempotency to actor and peer, persist task IDs and immutable input signatures, and choose a tested A2A binding. Store status updates separately or tag each with a monotonic revision. Use structured errors for authorization, unsupported protocol features, and cancellation. Namespace artifact references by peer and task and verify the returned region before reporting results.

## 5. Common Pitfalls & Debugging Playbook

### 1. A valid JSON object still causes an invalid operation

**Symptom:** The model sends fields matching the schema, but the requested action targets a resource outside the caller's scope.

**Root Cause:** The dispatcher treats a valid schema as sufficient authority.

**Diagnostic:** Review the trace from parsed arguments to the resource lookup. Check which actor and scope were used and whether both came from authenticated state.

**Fix:** Separate shape validation and authorization. Bind identity from verified request context and check tenant and resource ownership at the action boundary.

### 2. A delegated task appears twice after a timeout

**Symptom:** Two workers produce artifacts for the same requested work.

**Root Cause:** The caller retries an uncertain submission using a new ID, or assumes the peer provides deduplication without a shared contract.

**Diagnostic:** Compare client submission IDs, peer task IDs, and receipt timestamps. Reproduce a lost response after remote task creation in a test environment.

**Fix:** Use stable request identity, negotiate idempotency, and persist the remote task reference. Reconcile uncertain outcomes before resubmitting.

### 3. The status stream stops and the dashboard declares failure

**Symptom:** A connection resets while the remote task is working, and an operator later finds the task completed.

**Root Cause:** Transport lifecycle was confused with task lifecycle.

**Diagnostic:** Read the task's authoritative status by its ID and compare it with the last observed event.

**Fix:** Resume via a supported mechanism or poll within the remaining deadline. Preserve terminal task status and show “connection lost” independently.

### 4. The supervisor waits forever on an optional specialist

**Symptom:** Most branches finish, but runs never close when one dependency is slow.

**Root Cause:** The fan-out had no per-branch deadline, cancellation, or rule for partial answers.

**Diagnostic:** Compare branch launch and finish times with the run deadline. Inspect which branch was treated as mandatory.

**Fix:** Record required and optional branches explicitly. Enforce per-branch deadlines and merge policy. Return partial evidence with an explicit coverage gap when the contract permits it.

### 5. An SDK upgrade changes discovery or argument behavior

**Symptom:** The remote endpoint still responds, but newly submitted requests fail validation or return a state the client no longer recognizes.

**Root Cause:** A client assumed wire compatibility from a shared name without checking version, binding, or decoder subset.

**Diagnostic:** Capture the validated card, negotiated protocol and binding, and a redacted request/response pair. Compare the previous integration fixture with the new one.

**Fix:** Pin interoperable versions, run contract tests for sample tasks and terminal states, and keep version-specific adapters outside core workflow logic.

## 6. Three Standalone Practice Projects

### Project 1: Ticket Classification Router

**Domain:** Customer support

Route incoming requests into a fixed, published classification catalog. Keep the classification data and authorizer independent from the model. Different ticket text may be valid evidence for the same permitted category. Ambiguous cases should receive an explicit review status and the reason.

#### Recommended Folder Structure

Create router with schema.py, rules.py, and dispatch.py. Create tests with test_categories.py and test_review_routes.py. Place synthetic example tickets in fixtures.

#### Build Milestones

1. Design an output schema and enforce semantic limits after constrained decoding.
2. Check invalid categories, ambiguities, and consistent routing.

#### Acceptance Checklist

A known category produces a route and the source ticket ID. Unknown or invented keys fail validation. A valid but unauthorized department is denied. A pair of similar tickets with contradictory evidence goes to review with measurable criteria. Compare decisions after a schema revision and show how old records remain retrievable.

### Project 2: Food Recall Coordination

**Domain:** Food safety

A simulated quality team studies whether a listed supplier batch intersects a set of warehouse receipts. A supervisor requests separate evidence from inventory and supplier specialists, using synthetic data. Missing supplier evidence should leave the review open for an authorized person to verify.

#### Recommended Folder Structure

Create coordination with supervisor.py, inventory_evidence.py, supplier_evidence.py, and decisions.py. Add test_partial.py, test_disagreement.py, and test_lifecycle.py in tests.

#### Build Milestones

1. Define a supervisor contract, evidence format, and escalation deadline.
2. Test partial responses and prevent low-confidence findings from closing a case.

#### Acceptance Checklist

A complete review identifies exactly which data sources support the conclusion. Missing batch ranges do not yield a safe-to-close result. Slow dependencies stop at the deadline, while sufficient partial evidence remains available. Include an example conflict and show the stable decision record and review reason.

### Project 3: Media Licensing Task Exchange

**Domain:** Media licensing

Two independently deployed teams need to exchange requests for synthetic availability metadata. Use a versioned discovery contract and an explicit asynchronous task ID to allow delegation across framework boundaries. A studio can track its own request and cancel it while waiting.

#### Recommended Folder Structure

Create requestor with discovery.py, submission.py, and tracking.py. Create licensing_service with contract.py, tasks.py, and artifacts.py. Use tests for discovery, task authorization, replay, and cancellation.

#### Build Milestones

1. Specify Agent Card capabilities, task states, trust boundaries, and cancellation semantics.
2. Verify service discovery, a complete asynchronous task, and cancellation.

#### Acceptance Checklist

An unapproved peer or incompatible version is rejected before any work starts. A completed artifact carries the expected task ID, declared type, and verified usage data. Repeated submission obeys the documented idempotency contract. After a stream disconnect, the caller recovers task state without starting another task. Another caller cannot read or cancel the task.

- A. The model's embedding weights

### Q3. A client loses the stream just before it expects the final artifact. Which recovery path avoids duplicate work?

- A. Reconcile against the known task ID and resume or poll within the deadline
- B. Always submit another task with a new request ID
- C. Treat the previous task as completed

<details><summary>Answer & Explanation</summary>

**Answer: A.** A broken stream says little about the task. A task read or a supported resumption mechanism recovers authoritative state.

</details>

### Q4. Two agents can each transfer control to the other on ambiguity. What is the most direct lifecycle protection?

- A. Send them a larger shared transcript
- B. Use a stronger model for both
- C. Enforce allowed handoffs, history, and a finite hop count

<details><summary>Answer & Explanation</summary>

**Answer: C.** The allowed transitions and limit bound control flow even when both models repeatedly identify the same ambiguity. On exhaustion, return evidence or request review.

</details>

### Q5. A model selects a tool with an integer limit. Which check catches Python accepting True as the integer 1?

- A. Checking the exact decoded type
- B. Giving the parameter a shorter name
- C. Checking whether the value is truthy

<details><summary>Answer & Explanation</summary>

**Answer: A.** Python defines bool as a subclass of int. Use strict validation or an exact type check when the domain requires a real integer.

### Q6. Explain how to give two remote specialists access to only the data they need while retaining useful audit records.

<details><summary>Answer & Explanation</summary>

Resolve each specialist through trusted discovery and attach separate verified scope, deadline, and allowed input shape. Send only the evidence that specialist needs and keep the full request out of the delegation payload. Store the peer, caller, scoped request ID, remote task ID, resulting state, and artifact version or hash. Join records through trace context and operation IDs.

</details>

### Q7. A result reports “completed” but includes no artifact, and the domain requires an evidence record. What should the host do?

<details><summary>Answer & Explanation</summary>

Record both the remote state and the failed artifact validation. Check the task directly to rule out missed events. Require the expected type and fields and verify correlation and permitted content before finalizing the answer. If the peer cannot return evidence within the deadline, surface the incomplete result for review.

</details>
