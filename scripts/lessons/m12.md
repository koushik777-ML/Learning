## 1. The Mental Model

A useful agent combines a model that proposes a next step with a program that decides which steps are allowed, executes them, and records the result. Use this design when a request may need different information or sequences on different runs. Keep a deterministic workflow when its steps can already be described precisely.

Think of an operations desk. An assistant can suggest looking up a record or requesting review, while the desk has fixed procedures for who can see records, how calls are logged, and when the work stops. Connecting a model to a function list gives proposals a structured form. It does not grant permission or make those proposals correct.

### Decide where to let a model choose

| Situation | Suitable design | What you own in ordinary code |
| --- | --- | --- |
| Known form fields map to exact records | Deterministic route and lookup | Authentication, lookup keys, data validation, error contract |
| Which small read-only lookup to call depends on the request | Bounded ReAct-style loop | Tool allowlist, arguments, budgets, observation handling |
| A request has separable work stages and a reviewable sequence | Plan-and-execute with validated stages | Dependency ordering, input/output contracts, tool permissions |
| An answer or draft can be checked against explicit evidence | Generate, check, and conditionally revise once | Rubric, deterministic tests, revision budget, stop condition |
| A workflow crosses an organizational boundary | Standardized connector plus explicit approval or handoff | Identity, access delegation, state transfer, audit trail |

**ReAct** interleaves observations with choices. A model decides which allowed action to propose, sees what happened, and chooses a final answer or another step. It can adapt when the first lookup fails. Repeating steps eats latency and makes the flow harder to reproduce, so define which actions can repeat and how far the loop may go. Keep useful traces of tool names, arguments after redaction, call IDs, timings, and outcomes. Private reasoning is unnecessary for debugging the execution.

**Plan-and-execute** separates the model's requested sequence from actual operations. Validate that steps reference allowed operations, that dependencies exist, and that the total cost is bounded. Checkpoint after each completed stage. If evidence invalidates a remaining stage, ask for a revised plan or direct the known failure transition. A deterministic state graph is often enough to execute an already selected plan.

**Reflection** asks a second pass to detect a defect and suggest a revision. It helps when a rubric can catch omissions, such as a schedule that ignored a given holiday. A second model can share the original model's blind spots. Prefer deterministic checks for facts with direct representations, such as time window predicates and permitted IDs. Bound revision attempts and test whether the extra call improves outcomes enough to justify its latency.

### Separate the protocol, tools, and orchestration runtime

**Native tool calling** is the interface a model provider uses to describe allowed functions and return a structured proposal. **Model Context Protocol (MCP)** standardizes connecting a host to data and operations offered by external servers. **An agent framework** coordinates model calls, state, and execution. The three layers can work together. A local function can also be a tool with no MCP server. An MCP client can read a resource or call a tool from deterministic Python without any model.

A hosted MCP integration might make an authenticated server's tool visible to a model. The host should still select what is exposed, the server should authorize calls against the actual user, and both should validate inputs and outputs at their boundaries. Document capabilities independently of a vendor's model features so you can test them directly.

## 2. Core Architecture & How It Works Under the Hood

```text
 user request + authenticated identity
                   |
                   v
     host / orchestrator (state, policy, budgets)
        |                             |
        | model messages + schemas    | MCP client session
        v                             v
 provider model API           initialize + capability negotiation
        |                             |
        | proposed call id,          | list tools / read resource /
        | name, arguments            | get prompt / call tool
        v                             v
 host validates schema + policy  ---> trusted MCP server
        ^                             |
        | tool result linked by id    | database / curated records /
        +-----------------------------+ fixed business operation
        |
        +--> final response / next bounded step / human review
```

### Native function calling lifecycle

1. The application builds model input containing user-facing context and selected tool descriptions. A description should say what the tool does, which arguments it expects, and what a successful result means. Use a small selection. If several tool descriptions overlap in purpose, decisions become harder to test.
2. The model returns a final response or one or more call proposals. A proposal usually has an ID, function name, and arguments encoded as JSON or a structured object. A streaming API can return parts incrementally. Assemble all argument fragments for a call ID before parsing or considering execution.
3. The host resolves the name in a fixed registry. It validates the decoded data against local types, checks business and authorization rules using server context, enforces deadlines, and verifies any required approval. A schema-constrained model can still request another user's record, a nonexistent ID, or a valid action at the wrong time.
4. The host executes approved calls through adapters and normalizes results with status, data, and a bounded error shape. It sends each result back using the provider's expected association with the originating call ID. For example, OpenAI Responses APIs use a function-call output item linked with `call_id`. Other APIs may use a tool message with a provider-specific call identifier.
5. The host asks the model to complete or propose another action if the workflow budget permits. Independent reads can run concurrently after validation and remain associated with their call IDs. Dependent steps must run in order. If no permitted transition remains, return a clear status or ask a human to resolve the uncertainty.

Distinguish the provider's call ID, an application request correlation ID, and an idempotency key. The provider ID connects observations to model proposals. The correlation ID tracks an execution across services. The idempotency key identifies a logical business operation so repeat delivery cannot apply a change twice. For this lesson's read-only examples, retries can still be expensive and logging a repeated proposal is helpful.

### MCP primitives

| Primitive | Typical purpose | Example |
| --- | --- | --- |
| Tool | Typed callable operation, including computation or parameterized reads | Look up current opening hours for a supported site |
| Resource | URI-addressed data the client can select and read | A curated accessibility map |
| Prompt | Named reusable message template the client can surface | A visitor information draft with requested fields |
| Capabilities | Negotiated features for the client and server | Discover whether the server supports tools before listing tools |

Protocol discovery can include changes and pagination. Follow returned cursors when present. Namespace tool names locally so two servers cannot accidentally collide. Descriptions, annotations, prompts, and returned content are data from the server. A user or server identity still needs to be trusted and authorized by your application for each call. “Read-only” annotations can inform interface behavior, while executor policy is the enforcement mechanism.

### Transport and session lifecycle

MCP messages use JSON-RPC. Requests carry IDs for matching responses. Notifications have no expected reply. The client sends an initialization request containing protocol and capability information, processes the negotiated response, and completes initialization before using tools or resources. A disconnect can end a session or interrupt in-flight operations. Decide how clients reconnect and whether a call can safely replay.

**Stdio** runs a trusted local server process under the client, communicating over standard input and output. Server logs go to standard error because extra stdout text disrupts protocol framing. Startup parameters such as the executable, arguments, and environment are selected by the application. Run local services with appropriate filesystem and network permissions. Do not derive executable paths from a model proposal.

**Streamable HTTP** supports networked clients and separately deployed servers. A typical endpoint accepts HTTP POST for JSON-RPC messages and may use server-sent events for streaming protocol traffic according to the negotiated behavior. Manage TLS, authentication, origin checks, appropriate session handling, timeouts, and proxy streaming behavior. A session identifier associates protocol messages and must not substitute for authentication or authorization. Legacy HTTP+SSE is distinct from Streamable HTTP. A mismatch can look like an endpoint that opens correctly but never responds to subsequent calls.

### State, termination, and error semantics

Write a state shape with a request ID, actor context reference, goal, allowed capabilities, validated plan if present, remaining budgets, and finalized result. When retrying, resume at a known transition and require enough persisted information to determine what succeeded. Every step either advances, waits for a stated external signal, or terminates. Count model requests and tools, apply a wall-clock deadline, and detect no-progress transitions such as a repeatedly identical call.

Avoid giving textual tool errors authority to change system state. An observation may suggest how to present a missing resource, but it cannot authorize a new tenant, increase the budget, or download an executable on its own. Typed result categories make branches predictable. “Missing” can trigger a user clarification. “Permission denied” can terminate or lead to a grant workflow outside the agent. “Service unavailable” can trigger a bounded retry for operations that support it. A tail-latency incident can be isolated by checking these categories and per-step durations.

## 3. Complete Command, Query & Python Syntax Reference (Progressive)

### Validate arguments locally

```python
from typing import Literal
from pydantic import BaseModel, ConfigDict, ValidationError

class HoursArgs(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)
    garden: Literal["ridge", "river"]

try:
    args = HoursArgs.model_validate_json('{"garden":"ridge"}')
    print(args.garden)  # ridge
except ValidationError:
    print("Invalid lookup arguments.")
```

`Literal` restricts the field to supported values. `extra="forbid"` rejects unknown fields that could otherwise appear accepted while ignored. `strict=True` avoids many implicit conversions. `model_validate_json` validates a JSON input and returns a typed instance or raises a `ValidationError`. For a provider that accepts JSON Schema, `HoursArgs.model_json_schema()` produces a starting schema. Check that it uses only the provider's supported subset. Provider strict output and local validation complement one another. Per-actor access rules still apply when all arguments are valid.

A local dispatcher should conceptually do the following in order: find an allowlisted name, validate the arguments, establish actor and scope from trusted context, apply policy, enforce budget/deadline, call the implementation, and validate/summarize the result. Handling a model's unknown tool selection safely means returning an error the workflow can act on or halting. Never execute names by dynamic import, shell expansion, or reflection.

### Teach a model through the tool contract

A concise description might say “Return publicly posted opening hours for one known garden. This read-only lookup reports the regular schedule. It does not determine temporary closures.” This communicates capability and limits to a model and makes it easier to decide when a result is sufficient. If separate tools return regular schedules and closures, require both when answering whether a garden is currently open. Let deterministic time-zone code calculate local date and time when needed.

Schema field names should map directly to business terms. A model-friendly schema with an enum for “ridge” or “river” is better than an unconstrained arbitrary URL. A result with calendar date, time zone, status, and source timestamp is more useful than a free-form sentence alone. Structured output still needs validation and projection so the model receives the relevant fields without unnecessary personal data.

### MCP Python operations

```python
available = await session.list_tools()
names = {tool.name for tool in available.tools}
if "garden_hours" in names:
    result = await session.call_tool("garden_hours", {"garden": "ridge"})
    if result.isError:
        raise RuntimeError("The garden lookup did not complete.")
```

`list_tools` discovers server-declared tools after initialization. The return object contains tool definitions and can carry a continuation cursor on servers that paginate. `call_tool` takes a server-side name and a mapping of arguments. Tool computation errors are often returned with `isError`, while transport/protocol failures can also raise exceptions. Handle both. A result may include text, structured data, or other content blocks. Choose fields deliberately, validate their interpretation, and cap the data forwarded to the model.

For resources, `await session.list_resources()` discovers concrete resources a server lists. `await session.read_resource(AnyUrl("garden://access"))` reads the URI using the client's typed URL wrapper from Pydantic. Templates can describe parameterized resources separately. For a prompt, `await session.get_prompt("visit_brief", arguments={"garden": "ridge"})` returns message content to interpret under host policy. A prompt is useful when a known template needs versioning and reuse. Template content does not override host permissions.

### Choose a framework based on operational requirements

| Tool | Strength | Pressure test before adopting |
| --- | --- | --- |
| Plain Python | Transparent control flow and a small dependency surface | Can you checkpoint, inspect, and test the states once there are multiple pause/resume points? |
| LangGraph | Explicit graph transitions, checkpointing, and resumable workflows | What state lives in checkpoints and can edges replay safely? |
| OpenAI Agents SDK | Model/tool workflow, handoffs, and tracing integrated in the SDK | Do provider abstractions and tracing satisfy your runtime and privacy requirements? |
| PydanticAI | Typed dependencies, tools, results, and validation in Python | Are validation retries and dependency injection bounded and observable? |
| CrewAI | Task/role-oriented orchestration for collaborative sequences | Is the responsibility split clear enough to justify added calls, cost, and state management? |

A framework can implement repeated plumbing. It cannot define your access policy or invent the right stop rules. Begin by writing the failure transitions as tests. Check how each candidate framework records tool exceptions, enforces per-run budgets, exposes partial state, and handles privacy. A simple list/read/call flow is often easiest to understand in plain Python. Introduce a checkpointing runtime once workflow pause and resume are genuine requirements.

## 4. End-to-End Real-World Reference Example (Python-Centric)

A botanical garden publishes regular hours and a short accessible-entrance note for two venues. A trusted local MCP service exposes structured schedule lookups and a curated resource. The test drives the tool directly, which isolates transport and schemas from any model.

```text
garden-tools/
  server.py
  client.py
```

Install the MCP Python SDK in a Python 3.12 virtual environment using `python -m pip install "mcp>=1.13,<2"`. This uses the active interpreter's pip and constrains the example to the SDK's major-version line. Lock a tested exact version for a shared deployment.

### server.py

```python
from typing import Literal
from mcp.server.fastmcp import FastMCP

app = FastMCP("garden-information")
GARDENS = {"ridge": "09:00–17:00", "river": "10:00–16:00"}

@app.resource("garden://access")
def access() -> str:
    """Return the public accessibility note."""
    return "Ridge: step-free north gate. River: step-free west gate."

@app.tool()
def garden_hours(garden: Literal["ridge", "river"]) -> str:
    """Return the local opening window for the selected garden."""
    return GARDENS[garden]

@app.prompt()
def visit_brief(garden: str) -> str:
    """Draft a short visitor information prompt."""
    return f"Describe regular opening hours and entrance access for {garden}."

if __name__ == "__main__":
    app.run(transport="stdio")
```

`FastMCP` creates a named server. `@app.resource` binds the read operation to an explicit URI. `@app.tool()` registers the typed callable, deriving the argument schema and description from annotations and docstring. `Literal` limits fixture keys. `@app.prompt()` exposes reusable message content. `run(transport="stdio")` starts the local process transport. The source records are intentionally public. For restricted data, resolve identity and enforce per-actor policy before reading records.

### client.py

```python
import asyncio
from pathlib import Path
import sys

from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client
from pydantic import AnyUrl

async def main() -> None:
    server = StdioServerParameters(
        command=sys.executable,
        args=[str(Path(__file__).with_name("server.py").resolve())],
    )
    async with asyncio.timeout(10):
        async with stdio_client(server) as (read, write):
            async with ClientSession(read, write) as session:
                await session.initialize()
                tools = await session.list_tools()
                if "garden_hours" not in {tool.name for tool in tools.tools}:
                    raise RuntimeError("Expected garden_hours tool during discovery.")
                result = await session.call_tool("garden_hours", {"garden": "ridge"})
                if result.isError or result.content[0].type != "text":
                    raise RuntimeError("Unexpected lookup response.")
                print(result.content[0].text)
                notes = await session.read_resource(AnyUrl("garden://access"))
                print(notes.contents[0].text)
                invalid = await session.call_tool("garden_hours", {"garden": "other"})
                assert invalid.isError

if __name__ == "__main__":
    asyncio.run(main())
```

Run `python client.py`. It should print `09:00–17:00` followed by the note describing the north and west gates. The final assertion checks rejection of a garden outside the schema. The explicit interpreter keeps the child in the same environment, and the absolute path finds the file independent of the current directory. `asyncio.timeout(10)` bounds the full exchange, including startup and discovery. The nested async contexts release streams and shut down the server subprocess. `initialize` establishes negotiated capabilities before discovery and invocation.

To connect the tool to a model in a real integration, first expose only `garden_hours` through a model-native schema. Translate the structured proposal into the MCP call after schema and scope checks. Return the typed schedule as a bounded observation associated with the original call ID. Request a final answer with a source timestamp and allow the model to ask for clarification when the garden is unknown. Temporary closures require a separate reliable source. A tool's name alone does not entitle a final response to make that claim.

For networked operation, replace the trusted child process with a separately deployed Streamable HTTP service and an authenticated endpoint. Extend the integration test to cover session establishment, permission denial, reconnect behavior, and transport timeouts. Keep the contracts and fixtures the same so failures after the migration are attributable to the changed transport or policy path.

## 5. Common Pitfalls & Debugging Playbook

### Model proposed a valid call for the wrong record

**Symptom:** The arguments satisfy the schema but the host would disclose a record belonging to another actor.

**Root Cause:** Schema validation answers structural questions. It does not establish business permission or actor identity.

**Diagnostic:** Replay a permitted call and the same call for a different tenant. Inspect the authorization decision created from authenticated context at the execution boundary.

**Fix:** Enforce scope and policy in the tool server and client boundary. Give models narrow opaque IDs or constrained values, and test cross-actor rejection.

### Tool succeeded but the final answer ignores it

**Symptom:** The tool adapter logged a successful result, while the answer claims it did not have the lookup.

**Root Cause:** A provider call ID was lost, the result was formatted under the wrong message role, or its payload was truncated before being supplied back.

**Diagnostic:** Correlate each proposed call ID with its output message and downstream provider response. Check whether all chosen calls have exactly one associated result.

**Fix:** Use a typed adapter that preserves provider-specific result semantics and writes one result per executed call. Normalize large payloads before the next model request.

### Local server connects and then immediately disconnects

**Symptom:** The client starts but fails to initialize or raises a protocol parsing error.

**Root Cause:** The child may launch in the wrong interpreter, terminate at import, or emit application logs on protocol stdout.

**Diagnostic:** Inspect the exact child argv, interpreter, stderr, and first initialization message. Ensure no banner or debug prints are written to stdout by the server.

**Fix:** Use the intended interpreter and trusted script path. Send diagnostics to stderr and fail startup cleanly when dependencies are missing.

### A retry loop spends more time without new evidence

**Symptom:** The same read repeatedly returns unavailable and execution never reaches a response.

**Root Cause:** There is no no-progress transition or global deadline, or each local retry starts an independent unbounded budget.

**Diagnostic:** Record consecutive tool name, normalized arguments, error code, attempts, and remaining time.

**Fix:** Share a run-level deadline and terminate repeated no-progress choices. Retry only eligible failures with a bounded policy and surface the terminal status clearly.

### HTTP discovery works but long-running calls fail

**Symptom:** Short requests succeed. Calls that stream updates stall, time out, or fail during reconnect.

**Root Cause:** A reverse proxy may buffer streaming traffic or close idle sessions. A client may be configured for a different transport or session lifecycle.

**Diagnostic:** Verify transport negotiation and request/response content types. Compare direct and proxied behavior with a controlled short and long read. Inspect proxy timeouts and session log events.

**Fix:** Configure the documented transport consistently, size timeouts for observed latency, disable unwanted response buffering where needed, and cover reconnect with a deterministic integration test.

## 7. Mastery Checkpoint Questions

### Q1. What establishes that a tool-call argument is actually valid and authorized?

- A. Receiving valid JSON from the model alone
- B. Application-side schema validation and authorization before executing
- C. A large context window

<details>
<summary>Answer & Explanation</summary>

**Answer: B.** A model output is a proposal. Validate schema, permission, and policy at the execution boundary.

</details>

### Q2. Which MCP concept exposes contextual data for clients to read without treating it as an action?

- A. A resource
- B. An execution transcript
- C. A sampling temperature

<details>
<summary>Answer & Explanation</summary>

**Answer: A.** Resources expose contextual data. Tools expose executable operations and prompts describe reusable interactions.

</details>

### Q3. A model streamed two overlapping tool calls. The first finished generating its arguments while the second was incomplete. What should the host use to correlate received tool results?

- A. The order in which results returned
- B. The server session identifier
- C. The provider call ID associated with each tool proposal

<details>
<summary>Answer & Explanation</summary>

**Answer: C.** Assemble complete arguments per call ID, validate each permitted call, and send each result with its original identifier. Parallel execution can finish in a different order.

</details>

### Q4. Your Python stdio MCP server prints startup logs with print. The client now gets malformed JSON-RPC messages. What is the correct fix?

- A. Write application diagnostics to stderr and reserve stdout for protocol messages
- B. Prefix every log line with an HTTP status code
- C. Remove the initialization call

<details>
<summary>Answer & Explanation</summary>

**Answer: A.** In stdio transport stdout carries protocol data. Logging to stderr lets operators retain diagnostics without corrupting messages.

</details>

### Q5. A model keeps proposing the same unavailable read with identical arguments. How should the orchestration layer respond?

- A. Increase the token limit on every retry
- B. Enforce a shared deadline and terminate repeated no-progress choices with a useful status
- C. Send the failed request to every connected tool server

<details>
<summary>Answer & Explanation</summary>

**Answer: B.** A loop without evidence or state change should stop. Retry eligible temporary failures within a fixed budget, then expose the terminal information to the caller.

</details>

### Q6. Describe how you would move a public read-only tool from local stdio to Streamable HTTP and prove the migration preserved its contract.

<details>
<summary>Answer & Explanation</summary>

Keep the same names, schemas, and fixture results. Add TLS, endpoint authentication where needed, policy checks, and correct session handling. Update the client transport and initialize. Verify discovery, success and validation failures, timeout behavior, and reconnect with and without the proxy. The session ID helps correlate requests but does not replace identity or access checks.

</details>

### Q7. An application with a known two-read sequence wants to introduce an agent to improve flexibility. How would you choose between a deterministic graph and a model-driven loop?

<details>
<summary>Answer & Explanation</summary>

Use deterministic code for the known sequence, authorization, and final evidence checks. Introduce a model decision only where input meaning or incomplete evidence truly makes the next action variable. Test the model against representative intent and ambiguity cases, enforce a tool and time budget, and compare success, latency, and operational complexity with the deterministic baseline.

</details>

## 8. Curated Deep-Dive References & Official Documentation

### Review offline

When debugging an agent, identify the handoff that failed. A rejected proposal may be a model/schema problem or an intentional policy decision. A failed invocation may be an operation error or a transport interruption. A final answer that ignores a successful lookup can indicate a broken call ID association or a prompt that omitted the evidence. Trace these stages separately.

Choose tools, resources, and prompts according to how the consumer needs to use them. An operation with arguments belongs behind a typed callable. A known read-only artifact can have a stable resource URI. A reusable message template belongs behind a named prompt. For each interface write down scope, input, output, and failure expectations before integrating a model.
